# session-query-sqlite code notes

`packages/session-query/session-query-sqlite/src/index.ts:SqliteSessionQueryEngine.searchSessions`: a sessions cursor carried only the engine's process-local `_globalGeneration`. A second Host reconciling the same index file changes the persisted rows and `search_state.global_generation` but not this process's counter, so the first Host kept accepting a cursor against a different result set. The cursor generation is now `<local>:<shared>`, where `<shared>` is `search_state.global_generation` read from the database immediately before the page query (no `await` between the read and the query). Events cursors already bind to the persisted per-session `generation` read from the database, and live rows are connection-local (`temp.live_sessions`), so no other writer can change them.

`packages/session-query/session-query-sqlite/src/index.ts:SqliteSessionQueryEngine._reconcile`: `nextMainGeneration` was read before `BEGIN IMMEDIATE`, so two Hosts could both read generation N, both write N+1 for different changes, and a cursor taken between the two writes stayed valid. The generation is now read inside the write transaction, which also fixes the live-row generations derived from it. The observation of sources still happens before the transaction, so a Host can write rows computed from a snapshot that another Host has since changed; each persisted row carries its own revision, so the next reconciliation corrects it. Two Hosts sharing one index are therefore tolerated for cursor validity and lock contention, but remain unsupported as a design (each Host still reconciles the full set on its own).

`packages/session-query/session-query-sqlite/src/schema.ts:openSearchDatabase`: `PRAGMA busy_timeout = 5000` is set first, so a reconciliation that meets another process's write lock waits up to five seconds instead of failing at once with `SQLITE_BUSY`. The bound is a constant, not configuration.
