# cordis-client-runner code notes

`packages/extensions/cordis-client-runner/src/client/orchestrator.ts:CordisRunOrchestrator.drive`: the host's `resolveRequestRun` answers `accepted: false` when the run it holds changed while this page was loading the client half, and leaves the request pending. The page used to ignore that acknowledgement, so the request could stay unresolved with no failure shown (finding 39). `settleRequest` now reads it: a refused answer that names a run (a stale success, or a failure of a stale run) re-drives the whole plan, at most `MAX_STALE_REDRIVES` times, so `runHostHalf` re-attaches to the host's current run, or fails because the request no longer identifies the latest run, in which case that failure is answered to the host (it settles the request) and shown. A refusal after the last re-drive records a visible `client-half-failed`. A request another page settled first is recorded by `close` in `settledElsewhere` and is neither re-driven nor reported as a failure. A refusal of an answer that names no run (rejection, or a host-half failure before any run existed) is final.

`packages/extensions/cordis-client-runner/src/client/orchestrator.ts:CordisRunOrchestrator.answer`: a transport failure while answering is retried up to `ANSWER_ATTEMPTS` times back to back (no delay); after that it is logged once and recorded as a visible `client-half-failed` when the answer belongs to a plan, so the user sees the unresolved request instead of a console line. `decline` has no plan and keeps logging only, because its request has already been removed from the page.
