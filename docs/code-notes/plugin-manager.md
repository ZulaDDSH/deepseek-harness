# plugin-manager code notes

`packages/boot/plugin-manager/src/index.ts:PluginManager.updateBundle`: with HMR an update is a removal, an installation and, when the installation fails, a reinstallation of the removed version. Removal deleted the bundle from the ordered `dsh.profile.bundles` list and enabling appended it, so a successful update and a restored failed update both moved the bundle to the end, changing which bundle's overlapping settings win. The update now reads the bundle's index in the selection once the transaction owns the profile, keeps it in `selectionSlots` until `updateBundle` returns (the enable-failure path removes and installs twice), and `selectBundle` inserts a newly selected bundle at that index, clamped to the list length. A bundle that was not selected stays unselected.

`packages/boot/plugin-manager/src/index.ts:PluginManager.exclusive`: the removal and installation were separate `change` calls, each holding the package.json file lock only for itself, so another profile operation of the same Host could run between them (and between the failed install and the reinstallation). `change` now runs behind an in-process FIFO queue, and the update holds that queue for its whole replacement; the removal, installation and reinstallation it issues recognise the held queue through `AsyncLocalStorage` (`transaction`) and skip it, so they still take the file lock one by one and tests that spy on `installBundle` and `removeBundle` keep working. The network checks (`listBundles`, registry check, Git host probe) run before the queue is taken, because they change nothing. Operations queued behind an update wait without the `lockWaitMs` bound that a contended file lock has. The queue covers one `PluginManager`; a second process editing the same profile is still only serialized per operation by the file lock, and the README keeps that limit. Operations started from inside the update's own async context bypass the queue.

`packages/boot/plugin-manager/src/index.ts:PluginManager::removeBundle` (`restoreSelection`): removal deselects and unloads an enabled bundle before it asks pnpm to remove the package, because the files cannot go while the bundle runs, and a failure after that point (bundle still in use, pnpm exiting nonzero or timing out) left the still-installed package deselected and unloaded across restarts; an update that failed at its removal step inherited this because `updateBundle` returns before its reinstall (finding 103). The selection is now restored after either failure, but only when the package is still installed and its manifest is readable (`listBundles` reports it installed without an error); pnpm may already have deleted files, and re-enabling a half-removed bundle would only trade one failure for another. When restoring is unsafe or the restore itself fails, the original error stands and a warning says the bundle was left disabled. A restore at the pnpm-failure point reloads through `configure`, the same exclusion the earlier deselect used.
