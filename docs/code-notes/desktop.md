# desktop code notes

`apps/desktop/src/mandatory-update-policy.ts:DesktopMandatoryUpdatePolicy`: the policy started every process unblocked and was not persisted, so a restart cleared a known mandatory-update block and, when the policy service was unreachable or demanded fresh authentication, the failure preserved the new unblocked state. The constructor now accepts an optional `DesktopPolicyStore`; a mandatory decision (40005) is written to it when received, and the next process seeds its state from it so protected actions stay blocked until a fresh valid no-force response clears the record. The record is bound to the policy origin and the installed bundled dsh version, so an installed update (a different version) or a different deployment ignores a stale record and relies on the launch check. Offline recovery policy: there is none beyond that; an unreachable service keeps the block, and only a fresh no-force response or an installed version change releases it. The file is user-writable and is a durability aid, not a security boundary: deleting it clears the block, as would editing the product itself. Covered by `apps/desktop/tests/mandatory-update-policy.spec.ts`.

`apps/desktop/src/mandatory-update-policy.ts:fileDesktopPolicyStore`: reads tolerate a missing or corrupt file (treated as no record) and writes go through a temporary file and rename; write failures are swallowed because losing persistence must not break the in-process block.

`apps/desktop/src/file-actions.ts:installFileActions`: finding 311 showed that a direct download reserved its destination with an exclusive empty file, closed the handle and later removed that pathname when the download was cancelled or interrupted, so a file another process had moved into place after the reservation was deleted, including after a navigation cancellation had already retired the request. The reservation now records the device and inode of the file it created, and cleanup (`removeReserved`) removes the path only while it is still a regular file with that identity; a missing or replaced file is left alone. The check and the removal are two calls, so a replacement created between them is still not detected; a private staging file with an atomic publish would close that window and was not built. Covered by `apps/desktop/tests/file-actions.spec.ts`.

`apps/desktop/src/file-actions.ts:installFileActions`: finding 312 showed that the startup timeout stopped once Chromium announced the download, so a transfer that began and then went silent kept the request pending for the window's lifetime. A transfer inactivity timer (`DSH_DESKTOP_FILE_DOWNLOAD_STALL_TIMEOUT_MS`, default 300000 ms) now starts when the download starts in direct mode and is restarted by every `updated` event; on expiry the request rejects with a stalled error, the item is cancelled and the reservation cleanup runs from the `done` event. In save-as mode the timer arms on the first `updated` event only, because the native save dialog has no application deadline and a user choosing a path must not be reported as a stalled transfer; an `updated` event is taken to mean the dialog has closed (UNVERIFIED against Chromium, not run in a real Electron process). Covered by `apps/desktop/tests/file-actions.spec.ts`.

`apps/desktop/src/file-drag.ts:installDesktopFileDrag`: finding 310 describes a window between the final metadata check and the receiving application opening the borrowed original path in which the source can change. This is inherent to lending a live path to the operating system, so no snapshot was built: copying large originals into private temporary storage was judged a product decision (disk use, the 64 MiB export budget in `DragFiles`). The limit is documented in `packages/client/ui-file-drag/README.md` and `apps/desktop/README.md` instead.
