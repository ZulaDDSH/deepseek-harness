# python-sdk code notes

`python/sdk/src/deepseek_harness/client.py:HarnessClient::_fail_waiters` (generation guard): reader threads kept calling `_fail_waiters` after `close()` had returned, so a restart (`close()` then `start()`) received the previous runtime's "runtime closed" errors in its response waiters, subscriptions and the shared notification and request queues. The reader and stderr threads now carry the `Popen` they were started for. A stale thread delivers nothing and fails nothing once `self._proc` is no longer that process; the check and the puts happen under `self._lock`. `HarnessClient::start` also replaces `_notifications`, `_requests` and `_stderr_lines` with fresh objects, so errors queued by the previous `close()` and the previous runtime's stderr tail are not visible to the new runtime.

`python/sdk/src/deepseek_harness/client.py:HarnessClient::start` and `api.py:DeepSeekHarness::start` (`_lifecycle`): `_proc` was checked and set without a lock, and `DeepSeekHarness.start` checked `_initialized` before starting and initializing, so two threads using a fresh instance both spawned a runtime and both initialized. One reentrant lifecycle lock, owned by the client and reused by `DeepSeekHarness`, serializes `start`, `initialize` and `close`; both paths re-check their condition after taking it, and the unlocked early return is only a fast path for an already initialized instance. The lock is not `_lock`: `_lock` guards short state updates and is taken by the reader thread, while lifecycle operations wait on subprocesses.

`python/sdk/src/deepseek_harness/client.py:_BoundedQueue`: notification, request and subscription queues had no bound, so an unread subscription or an unread default queue grew without limit while the runtime kept emitting. Each queue now holds at most `NOTIFICATION_QUEUE_LIMIT` items plus one reserved slot. When an item does not fit, a `NotificationOverflowError` takes the reserved slot, the queue stops accepting items, and the consumer reads the already queued items first and then the error. A subscription that overflows is removed from the client, so it no longer receives; other subscriptions are unaffected. Terminal errors (runtime closed) are still delivered because they use the reserved slot only when it is free. A dropped incoming runtime request is visible as the same error on `next_request`; the runtime is not answered for it.

`python/sdk/src/deepseek_harness/client.py:_StderrTail` and `HarnessClient::_stderr_loop`: the stderr tail was bounded by line count only and `for line in proc.stderr` buffers an unterminated line without limit. The loop now reads at most `STDERR_LINE_LIMIT` characters per call, marks a line that exceeds it as truncated and discards the rest of that line in bounded chunks, and `_StderrTail` evicts the oldest lines once the UTF-8 size of the kept lines exceeds `STDERR_TAIL_BYTES`, in addition to the line cap.
