# credentials-local code notes

`packages/credentials/credentials-local/src/windows-acl.ts:windowsAclViolations`: Windows has no mode bits, so the owner-only promise made on POSIX was unenforced and a document in a directory that grants Users or Everyone read was served without complaint. The check now reads the file's DACL as SDDL through `icacls /save` (the SDDL form names trustees by SID or fixed abbreviation, unlike the localized account names in normal `icacls` output) and reports every allow entry whose trustee is not the current user's SID, SYSTEM (`SY`/`S-1-5-18`), Administrators (`BA`/`S-1-5-32-544`) or Owner Rights/Creator Owner (`OW`/`CO`). The current SID comes from `whoami /user`, and both tools are started from `%SystemRoot%\System32` rather than `PATH`. Deny entries are ignored; they can only narrow access.

`packages/credentials/credentials-local/src/windows-acl.ts:restrictToOwnerWindows`: a newly created document inherits its directory's DACL, so after each write the provider removes inheritance and grants full control to the current user, SYSTEM and Administrators only (`icacls /inheritance:r /grant:r`). A replacement keeps the target's DACL (see the fs-local DACL-preservation note), so this only changes a first creation. There is a short window between creation and restriction in which the file carries the inherited DACL; a directory that must never expose it should itself be restricted. `src/index.ts:assertOwnerOnly` now throws on Windows with the exact `icacls` command when a violation exists, matching the POSIX `chmod 600` refusal. The check is the same in-process and cross-process: it inspects the file, not the process. It is verified only against Windows `icacls` output on one machine; domain accounts, UAC-filtered tokens and localized Windows are unverified.

`packages/credentials/credentials-local/src/index.ts:assertOwnerOnly`: on Windows each check spawns `icacls`, which is slow enough to break the debounce timing of live reloads, so a watcher-triggered reload (`reconcileFromDisk(true)`) reuses a clean verdict younger than five seconds; boot and every write path (which reconcile first) always inspect afresh. `src/index.ts:protectOnWindows` skips a path that does not exist, which is the case when the atomic write is stubbed in tests, and only a regular file is inspected (a directory takes the normal read error). Covered by `packages/credentials/credentials-local/tests/local.spec.ts` (Windows-only case).

`packages/credentials/credentials-local/src/index.ts:LocalCredentialProvider::commitDocument`: the product lock is advisory, so an editor that saves between the provider's read and its atomic replace used to be overwritten from the earlier cached text (finding 160). Every writer now re-reads the file immediately before replacing it; if the text differs from the cache it folds the edit in (`reconcileFromDisk`) and re-renders, up to three attempts, then fails with nothing written rather than clobber. A residual window of one `rename` remains, because POSIX and Windows offer no compare-and-swap replace. `modifyRecord` runs its async `mutate` (an OAuth refresh) before the commit: if the record it mutated was itself changed on disk meanwhile, the commit is refused as a conflict, because applying a result computed from a superseded record would silently discard the user's edit; an edit to any other entry is folded in. The refused refresh result is lost, so a provider with rotating refresh tokens must treat the conflict as a re-authorization trigger.
