# webhook code notes

`packages/experimental/webhook/src/journal.ts:WebhookJournal` and `packages/experimental/webhook/src/index.ts:WebhookRuntime::dispatch` (finding 108): `dispatch` returned before any rule ran and kept every accepted delivery only in memory, so a Host crash after the adapter answered `202`, or a rule failure, lost the work with a log line. The runtime takes `journalFile` (`packages/experimental/webhook/src/types.ts:WebhookRuntimeConfig`); see the default-journal note below for when it is on. With the journal on, `dispatch` appends one `add` record (the frozen delivery and the ids of the rules that match it) and fsyncs it BEFORE it starts any rule, still synchronously, so an adapter that calls `dispatch` and then answers has persisted the delivery first; a write failure or a full journal throws from `dispatch`, which the GitHub adapter already maps to `503`. Each rule outcome is then appended (`done`, `fail`); an entry disappears when every rule it names is done. The file is an append-only JSON-lines log rather than a rewritten snapshot because a delivery body can be megabytes and `dispatch` is synchronous on the event loop; it is compacted to the live entries on load and after `COMPACT_AFTER_RECORDS` appends, and a torn final line from a crash mid-append is dropped. Any other malformed line makes the constructor throw, so a damaged journal is never silently discarded.

`packages/experimental/webhook/src/index.ts:WebhookRuntime::register` (finding 108) replay: it runs, for the registering rule id, every journaled entry in which that rule is still `pending` (a Host crash, or a disposal abort, interrupted it). Each replay appends an `attempt` record first and gives up after `MAX_REPLAY_ATTEMPTS`, marking the rule `failed`, so a delivery that crashes the Host on every start cannot loop forever. A rule that throws for a reason other than disposal is marked `failed` with a truncated message and is NOT retried: a failed rule's `fail` record stays in the file (and in the Host log) as the operator-visible record, and replaying it is a manual action (delete the record or the file). Interrupted-by-disposal rules stay `pending` and replay at the next registration of that rule id, including in the same process.

`packages/experimental/webhook/src/journal.ts:WebhookJournal::add` (finding 108) bound: at most `MAX_JOURNAL_ENTRIES` live entries. A full journal first evicts the oldest entry in which no rule is pending (already settled, only failure records are left); when every entry still has pending work, `dispatch` refuses with an error instead of evicting it, because dropping un-run accepted work would be the silent loss this fixes. Disk use is bounded by that count times the adapter's body limit.

`packages/experimental/webhook/src/journal.ts:WebhookJournal` (finding 108) limits: delivery is at-least-once. A crash after a rule admitted its prompt but before its `done` record is flushed replays the rule and can create a second Session; rules already own idempotency through `source.deliveryId`. A pending entry whose rule id is never registered again stays until evicted. `packages/experimental/webhook-github/src/handler.ts:createGitHubWebhookHandler` still answers `202` after `dispatch` and its replay-window memory is still per process, so a redelivery of the same body after a restart is accepted again and relies on rule idempotency.

`packages/experimental/webhook/src/types.ts:WebhookRuntimeConfig` (finding 108): `packages/experimental/webhook/src/types.ts:WebhookRuntimeConfig::journalFile` is the absolute path of the delivery journal, or `false` to disable it; omitting it uses the Host data directory when one is available (see the default-journal note below). It is a plain interface read by `packages/experimental/webhook/src/index.ts:WebhookRuntime::constructor`, not a Schemastery `Config`, because `@deepseek-ai/schemastery` is not a dependency of this package, so no generated config catalog entry exists for it. The field carries no JSDoc because the comment guard rejects it; this note and the package README are its documentation.

`packages/experimental/webhook/src/index.ts:WebhookRuntime::constructor` default journal (finding 108 follow-through): nothing in a shipped composition ever set `journalFile`, so the journal was unreachable. The constructor now resolves it as: `journalFile: false` is the opt-out (no journal); a string is used as given (absolute path required); when omitted it falls back to `<DSH_HOME>/data/webhook/journal.jsonl` obtained from the Host's `dshPath` service (`packages/boot/app-boot/src/index.ts`, provided on the root context), category `data` because losing the file loses accepted deliveries. The service is read with `ctx.reflect.get('dshPath')`, not `ctx.dshPath` and not `static inject`: a plain read of an unprovided service throws and a required inject would stop the runtime loading in any context that has no Host path service, and `@deepseek-ai/dsh-home-paths` cannot be imported because it is not a dependency of this package. A context without the service (unit tests that build a bare `Context`, embedders that do not use app-boot) therefore keeps the in-memory behaviour. The service is read once at construction, so a `dshPath` provided by a plugin that loads after the runtime is not seen. Consequences of the default being on: a damaged (non-torn) journal makes the constructor throw and the runtime does not load until the file is repaired or `journalFile: false` is set, and a journal holding `MAX_JOURNAL_ENTRIES` unfinished deliveries makes `dispatch` throw (the GitHub adapter answers `503`). Limit: the file is not locked, so two Host processes (or two isolated webhook runtimes) sharing one `DSH_HOME` would append to and replay each other's entries; set `journalFile` per process (or `false`) in that setup.
