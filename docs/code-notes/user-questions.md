# user-questions code notes

`packages/interaction/user-questions/src/projection.ts:applyUserQuestionEvent` (finding 53): a PTC `ask_user_question` sub-call used to enter the fold only from its settled `tool/ptc-dispatch` pending result. If the `run_code` process ended before that record, the question the user had been shown vanished and a late answer settled nothing. The fold now admits the sub-call as `open` from `tool/ptc-dispatch-start`, which the executor appends before the tool body runs and before any wait, using the stable `subCallId` as the call identity. A later `tool/ptc-dispatch` then moves it to `continued` (pending result), settles it (answer batch), or drops it (error result, which includes abort and cancel, matching native `tool/result` handling).

The crash case has no dispatch record at all: session resume repair appends the synthetic `TOOL_OUTCOME_UNKNOWN` result to the root `run_code` call. `applyUserQuestionEvent` treats that root result like the native unknown-outcome rule and promotes every still-open question whose id starts with `<rootCallId>:ptc:` to `continued`; any other root result drops them, since a normally finished or cancelled run has already recorded a dispatch result for each started sub-call. The prefix match relies on the documented `<parent>:ptc:<n>` id shape; sub-calls logged with an older opaque id carry no start-time identity and are still reconstructed only from their pending dispatch result. In `packages/interaction/user-questions/src/projection.ts:applyUserQuestionEvent` the start is admitted without the `fold.timed` check because a PTC header lists only `run_code`; a legacy blocking `ask_user_question` made through PTC is therefore also admitted and shows as continued after an interrupt (documented in the README). A non-pending, non-error dispatch result drops the entry rather than settling it, so in-time PTC answers still never reach `settled`, as before. `userQuestionProjectionDefinition.stateVersion` is bumped so stored caches refold.

`packages/interaction/user-questions/src/index.ts:UserQuestionService::ask` (findings 273, 274): only the timed `ask_user_question` tool checked that question ids were unique, and no path checked option labels, although answers identify a question by its id and an option by its label. A blocking call with repeated ids returned two indistinguishable answer entries and could not build its answer transcript, and two options with the same label were both marked selected by one click and returned an ambiguous label. `ask` is the admission boundary shared by the blocking tool, the timed tool (through `askTimed`) and approval callers, so it now rejects an empty or repeated question id with `BAD_QUESTION_ID` and a repeated option label within one question with `DUPLICATE_OPTION`, after the live-agent check and before any provider interaction. The timed tool keeps its own earlier unique-id argument error.

`packages/client/ui-user-questions/src/client/QuestionComposer.tsx:QuestionComposer` (finding 272): option buttons carry radio or checkbox roles, but an Enter handler cancelled their native activation and submitted the existing drafts, so a keyboard user who focused another option and pressed Enter submitted the previous (often recommended preselected) choice, and with no prior choice only got an incomplete-answer message. The handler is removed so Enter on a focused option activates it exactly like a click (selects or toggles it, and a single-select choice advances), and submitting the batch always needs the explicit submit action. Enter in a text answer still continues the flow.

`packages/client/ui-user-questions/src/client/index.ts:QuestionCards::liveKeysFor` (finding 271): a mounted question composer pruned the persisted drafts to the keys of cards registered in this browser, but a continued question gets its card when its Session projection is reconciled while an open question gets one only when its forwarded request arrives, so a composer that mounted before another answerable question had a card deleted that question draft permanently. `publishContinuedQuestions` now records, per Session, the keys of every active row of the loaded `userQuestions` projection (open and continued), and `liveKeysFor` returns those joined with the registered card keys. While a Session projection has not loaded, `liveKeysFor` returns undefined and `QuestionComposer` skips the prune, so drafts are only discarded against an authoritative live-call set; a prune that was skipped is not retried by that composer, and a stale draft is still removed when its card closes.
