# CI workflow code notes

`.github/workflows/weighted-approval.yml:publish-status`: the job and `weighted-approval-review-event.yml:record-review-event` were guarded by the literal `github.repository == 'deepseek-harness/deepseek-harness'` and the App token step named that owner and repository, so a fork (the reviewed remote is `ZulaDDSH/deepseek-harness`) skipped both jobs and never published the `weighted approval` status. The guard now compares with `vars.WEIGHTED_APPROVAL_REPOSITORY`, falling back to the upstream name when the variable is unset, and the token step uses `github.repository_owner` and `github.event.repository.name`. Not changed: `pr-check-after-approve.yml` hardcodes the same owner and repositories for its own App token, and `check-approval.mjs` takes the repository from the event payload. Runtime behaviour is unverified: it needs a run in a fork with the variable set and the App installed, and whether the fork's branch rules require the status was not checked.

`.github/workflows/pr-check-on-head-branch.yml:pre-merge`: the job merged the base into the pull request head and ran `scripts/pre-merge-check.ts` from the merged tree, so a pull request could replace the driver with a script that exits 0 and the base-controlled workflow accepted it, even in `block` mode. The run step now restores the driver and the scripts it runs directly (`trusted=(...)`: the driver, `verify-version-sync.ts`, `verify-upgrade-guides.ts`, `compile-referenced-projects.ts` and `release/process.ts`, which the compile script imports) from `BASE_SHA` with `git checkout BASE_SHA -- <files>` before executing, and reports a base commit that lacks one of them by mode (error in `block`, warning in `report`). The list lives in the workflow because the workflow definition comes from the base under `pull_request_target`; `scripts/pr-check-on-head-branch.spec.ts` checks that it covers every script `preMergeSteps` names and the local modules they import, and runs the step against a temporary repository whose head replaces or deletes the driver. `scripts/pre-merge-check.ts:preMergeSteps` calls `scripts/verify-upgrade-guides.ts` through `pnpm exec tsx` instead of the `verify-upgrade-guides` package.json alias, which the pull request could redefine. Not covered: the install, `generate-typert.ts` and the other files the compile scripts load by URL, the tsconfig and package.json graph, dependency lifecycle scripts and `pnpm/action-setup` still come from the pull request, so the status proves that the base-controlled driver ran, not that the pull request's build instructions are trustworthy; a change to those still needs review. A base commit without the driver (the pull request that introduces it) reports instead of running. Runtime behaviour on GitHub is unverified; the step was exercised only through bash against a local repository, and whether a branch rule requires `Policy / Pre-Merge Check` was not checked. `.github/AGENTS.md` line 9 still says the check script changes together with the build in the same pull request.
