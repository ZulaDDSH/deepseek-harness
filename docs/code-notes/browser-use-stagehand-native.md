# browser-use-stagehand-native code notes

## packages/experimental/browser-use-stagehand-native/src/worker-client.ts:openBrowserWorker (issue 331)

The Worker `ready` request and every browser operation could wait forever: the SDK bounds only navigation and the three model-assisted calls, and only when it is healthy, while tab operations, screenshots and initialization have no SDK deadline at all. `openBrowserWorker` now bounds each request to `operationTimeoutMs` plus a fixed 15 seconds, capped at the 32-bit timer limit. The extra time keeps the host deadline after the SDK's own action timer, which Stagehand arms ten seconds after the configured timeout, so a healthy SDK still reports its own failure. The timer is owned by the host request in `worker-rpc.ts:request`, not by the caller's signal, because the Worker and the Session's reservation outlive a canceled caller. When `ready` expires the Worker is terminated and the open fails, so the Session's acquisition is rolled back and a later call retries it. When an operation expires, `execute` closes the connection through the same drain-or-terminate path as a canceled call. If SDK requests do not drain within `shutdownGraceMs` the error is a `StagehandDrainError` that carries the timeout in its message, the connection stays unusable, and the reservation is retained until disposal verifies cleanup. If cleanup succeeds, the call fails with `StagehandTimeoutError` (code `STAGEHAND_WORKER_FAILED`) and `index.ts:apply` drops its connection, so the next call opens a fresh Worker against the same browser. The tool definitions declare no `timeoutMs`, so the shared tool timeout policy is not involved and a profile without it is still bounded.
