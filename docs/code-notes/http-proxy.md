# http-proxy code notes

`packages/util/http-proxy/src/policy.ts:bypassesProxy`: finding 365 showed that a `NO_PROXY` entry such as `10.0.0.0/8` was read as a host name and never matched, so internal addresses an operator meant to keep direct were tunnelled through the proxy without any diagnostic; an entry containing `/` is now read as an IPv4 or IPv6 CIDR block, matched with `node:net` `BlockList` against a destination that is an IP literal (an IPv4-mapped IPv6 destination matches IPv4 blocks), and a malformed block (bad address, non-numeric or out-of-range prefix) matches nothing; routing goes through `proxyForUrl`, so the installed dispatcher and `proxyRouteFor` keep giving one answer, but a spawned Node child under `NODE_USE_ENV_PROXY` still applies Node's own matcher, which has no CIDR support.

`packages/util/http-proxy/src/install.ts:installProxyFromEnvironment`: finding 364 showed that a SOCKS, PAC, or malformed proxy value is reported and the affected scheme left direct, which is fail-open for an operator who treats the proxy as an egress boundary; setting `DSH_PROXY_FAIL_CLOSED` to `1` or `true` in the launch environment now makes `installProxyFromEnvironment` and `createRouteDispatcher` throw with every rejection message before anything is installed, so startup stops instead of connecting directly; without it the documented fall-back is unchanged, and an absent proxy never triggers the failure because only a rejected value is a diagnostic.

`packages/util/http-proxy/src/install.ts:installGlobalProxy`: finding 366 showed that each installation restored the dispatcher, policy, and environment it captured regardless of who else was installed, so disposing an outer installation first replaced the live inner policy and left the inner disposer restoring a closed dispatcher; installations are now a stack serialized through one lifecycle queue, a disposer refuses with an error before changing any state unless its installation is the newest live one, and a disposer called a second time does nothing.
