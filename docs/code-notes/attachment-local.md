# attachment-local code notes

`packages/attachment/attachment-local/src/file-quota.ts:FileStoreQuota`: verbatim files had no size limit and nothing deleted them, so any caller of `saveFile` / `saveFileStream` (an upload route, including a LiveShare reader holding `fileUploads/upload`) could fill the host volume (finding 30). The quota refuses one file above `maxFileBytes` and refuses growth of `file-objects/` above `maxStoredFileBytes`. Usage is scanned once from `file-objects/` on first use, then updated when an upload publishes a digest that did not already exist; bytes of in-flight uploads are reserved chunk by chunk so concurrent uploads cannot jointly overshoot, and are released when the upload finishes or fails. Streamed bodies are refused while streaming, so an oversized upload never completes its staging file. Re-uploading an existing digest consumes no quota when the whole body is in memory (`saveFileVerbatim` checks existence before reserving); a streamed body is metered before its digest is known, so a duplicate that does not fit in the remaining room is still refused. Automatic garbage collection is not implemented: resumed and forked Sessions share objects and no reference model exists yet, so unreferenced objects stay until an operator deletes them.

`packages/attachment/attachment-local/src/file-store.ts:saveFileStreamVerbatim`: takes an optional quota; `existsSync` on the digest path inside `targetFor` decides whether the published object is new for quota accounting. A concurrent identical upload can be counted twice, which only errs towards refusing.

`packages/attachment/attachment/src/error.ts:ATTACHMENT_ERROR_CODES`: `FILE_TOO_LARGE` (one file above the backend's per-file limit) and `FILE_STORE_FULL` (the backend's total file budget is exhausted) are raised by the local backend and reach the browser as the `reason` of `session/attachment-invalid`; the Web UI has no dedicated text for them and shows its generic send-failed text with the code.
