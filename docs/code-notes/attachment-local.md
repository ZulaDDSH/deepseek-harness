# attachment-local code notes

`packages/attachment/attachment-local/src/file-quota.ts:FileStoreQuota`: verbatim files had no size limit and nothing deleted them, so any caller of `saveFile` / `saveFileStream` (an upload route, including a LiveShare reader holding `fileUploads/upload`) could fill the host volume (finding 30). The quota refuses one file above `maxFileBytes` and refuses growth of `file-objects/` above `maxStoredFileBytes`. Usage is scanned once from `file-objects/` on first use, then updated when an upload publishes a digest that did not already exist; bytes of in-flight uploads are reserved chunk by chunk so concurrent uploads cannot jointly overshoot, and are released when the upload finishes or fails. Streamed bodies are refused while streaming, so an oversized upload never completes its staging file. Re-uploading an existing digest consumes no quota when the whole body is in memory (`saveFileVerbatim` checks existence before reserving); a streamed body is metered before its digest is known, so a duplicate that does not fit in the remaining room is still refused. Automatic garbage collection is not implemented: resumed and forked Sessions share objects and no reference model exists yet, so unreferenced objects stay until an operator deletes them.

`packages/attachment/attachment-local/src/file-store.ts:saveFileStreamVerbatim`: takes an optional quota; `existsSync` on the digest path inside `targetFor` decides whether the published object is new for quota accounting. A concurrent identical upload can be counted twice, which only errs towards refusing.

`packages/attachment/attachment/src/error.ts:ATTACHMENT_ERROR_CODES`: `FILE_TOO_LARGE` (one file above the backend's per-file limit) and `FILE_STORE_FULL` (the backend's total file budget is exhausted) are raised by the local backend and reach the browser as the `reason` of `session/attachment-invalid`; the Web UI has no dedicated text for them and shows its generic send-failed text with the code.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.requestVersion`: request-image generation is shared per variant id, which digests the attachment id and target only, so concurrent callers with the same bytes but different display metadata (name, `originalDimensions`) share one generation. The shared result now carries the verified reference of the caller that started it, so each caller gets its own reference back after it is checked against the shared one for attachment id, media type, byte count and dimensions; a mismatch raises `ATTACHMENT_CORRUPT` instead of returning another occurrence's reference (finding 354).

`packages/attachment/attachment-local/src/compression-limiter.ts:CompressionLimiter.run`: takes an optional signal; a task still waiting for a slot is removed from the queue when the signal aborts (and one already aborted never queues), so cancelled work never retains its inputs or runs later. A task that already started keeps running because the image library offers no cancellation. `LocalAttachmentStore.saveImages` aborts a per-batch signal from inside the failing task, before the limiter releases the slot, so the remaining queued images of a failed batch are dropped and cannot be started by the freed slot; shared request-image work passes its own signal so a request cancelled by every caller leaves the queue. The queue itself is still not capacity-bounded: the per-message image and byte limits bound each batch, and a bound on pending batches would need a new Config field (finding 355 partial).

`packages/attachment/attachment-local/src/store.ts:inspectMetadata`: an animated source image (more than one frame) is refused with `INVALID_IMAGE` instead of being normalized to its first frame, because the durable still reference and the model replay cannot show later frames and the composer gave no warning. Conservative default for finding 356: refuse rather than silently flatten; a single-frame GIF is unaffected and still re-encoded, and the user can attach the animation as a file. `detectImage` and `canPassThroughNormalization` still report animation so the refusal stays at the admission boundary.

`packages/attachment/attachment-local/src/store.ts:ensureDurableDirectory`: the `chmod(0700)` now applies only to store-owned directories (staging and object buckets); `ensureDurableHome` passes `restrict: false`, so a pre-existing user-selected harness home keeps its mode bits (group access, setgid) while a home the store creates is still made with mode `0700` by `mkdir`. The durability sync walk is unchanged and independent of the mode change (finding 351).

`packages/attachment/attachment-local/src/store.ts:sweepStagingDirectory`: a crash between creating a staging file under `attachments/v1/tmp` and unlinking it left that file forever. The first staged write per process and staging directory removes UUID-named regular files whose mtime is older than `STALE_STAGING_MS` (24 h); a live writer refreshes its mtime on every chunk, so its file is never old, and a file linked into `objects/` before the crash is only a second name for the published bytes. The sweep is best-effort and silent on failure; it does not report or cap retained temporary bytes, and a writer stalled for more than a day would lose its staging file (finding 352 partial).
