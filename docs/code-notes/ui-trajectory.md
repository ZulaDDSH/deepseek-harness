# ui-trajectory code notes

`packages/client/ui-trajectory/src/index.ts:SessionToolResults`: the live value store was bounded by count only, so a few large canonical values (or many across Sessions) could stay resident until count eviction, Session disposal or plugin unload (finding 57). Each value is now measured once by its JSON text length (a lower bound of its heap size, one transient string at admission). A value above `maxValueBytes` is never retained and the inspector shows the existing unavailable state; a Session whose retained values pass `maxBytesPerSession` evicts its oldest values first; `maxTotalBytes` bounds all Sessions together, and a new value that still does not fit after evicting that Session's own oldest values is dropped. Sizes follow a value when its key changes from the call id to the event sequence. The sum of `maxBytesPerSession` and `maxResultsPerSession` limits is not an exact memory ceiling: JSON length undercounts object overhead and a value being measured is briefly held twice.

`packages/client/ui-trajectory/src/index.ts:SessionToolResults.watch`: finding 56 (a Session reader allowed `toolResults/watch` receives the canonical post-policy value, which rendered-content redaction does not touch) is not fixable inside this package. The Host cannot tell a policy-redacted result from an ordinary one, and the endpoint's audience is decided by LiveShare (`packages/experimental/liveshare/src/endpoint-classification.ts` classes it `reader-session-read` and `viewer-access-policy.ts` lists it in `VIEWER_SESSION_READ_ROLE`). The README states the exposure; the audience change belongs to LiveShare.

`packages/client/ui-trajectory/src/index.ts:SessionToolResults` (`tools/result` handler): a second result for a call id that is still pending replaced the stored value but added its size again, so `state.bytes` drifted upward and evicted live neighbours early; the prior entry's size is now subtracted and its entry removed before the new one is counted.
