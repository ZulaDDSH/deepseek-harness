# agent-instructions code notes

`packages/context/agent-instructions/src/files.ts:loadBaselineInstructionSet` (finding 31): the per-file `maxSourceBytes` cap did not bound the batch, so a deep tree of near-limit files was read and retained before rendering applied `maxBytes`. Each chain (user-global, project) now reads candidate groups (one directory, or the two user-global roots) most-specific-group-first and stops once `AGGREGATE_READ_FACTOR * maxBytes` bytes were read (a file that crosses the budget is still read, bounded by `maxSourceBytes`). Unread broader candidates are not in `observed` and are appended to `rendered.omitted`. A group is always read whole, never split, because the earliest duplicate in a group wins in dedup and reading it last would change which file is kept; all candidates including duplicates count toward the budget; the factor leaves room for the usual AGENTS.md/CLAUDE.md pair. The renderer keeps a most-specific suffix per chain, so skipped broader files could not have been rendered once the budget was spent unless dedup collapsed read files.

`packages/context/agent-instructions/src/index.ts:compose` (finding 49): not a bug. Every `agent/pre-step` calls `compose`, which passes `includeBaselineScopes: keepVisibleBaseline` to `state.ts:reconcileInstructionContext`, so all baseline scopes (user-global and every ancestor candidate) are re-probed by version each step with no filesystem touch. The only delay is the `pending.length > 0` early return in `compose`, which reuses the already queued message for one step. The README limitation wrongly said refresh was touch-driven; the test `reports an externally edited project instruction at the next pre-step without a filesystem touch` pins the behaviour.
