# acp code notes

`packages/acp/acp/src/index.ts:apply` (`notify`): the bridge notifier caught every transport write failure and only logged it, so the session's delivery handler never saw it and a prompt could resolve successfully although its assistant update was not delivered. The notifier now returns the connection's rejection unchanged. `AcpSession::enqueue` decides per update kind: a failed assistant update sets `inflight.outputError`, which makes the prompt reject with `assistant output delivery failed`; failed tool-call, tool-result and config-option updates are optional, are logged, and do not fail the prompt. The ACP SDK closes its connection on a write failure, so later updates of that connection fail the same way.

`packages/acp/acp/src/session.ts:AcpSession::enqueue`: updates ran in a per-session promise chain with no bound, so a client that stopped reading without closing the transport (or a notifier promise that never settles) left prompt settlement, permission requests, `close` and bridge teardown waiting on that chain, and later events piled up behind it. Every link now runs under `UPDATE_DELIVERY_TIMEOUT_MS` and the queued bytes (an estimate: the JSON length of the event data) are capped at `MAX_PENDING_UPDATE_BYTES`. Either limit calls `failOutput`: it records the failure, logs it once, and calls `onOutputFailure`, which the bridge wires to `connection.close(error)` so a stalled transport is closed. After that every queued or later update fails at once with the recorded error instead of waiting, so `drainUpdates`, prompt settlement and `AcpSession::close` finish in bounded time, `close` still runs descendant disposal, the persistence flush and Agent disposal, and a prompt whose assistant update was lost rejects instead of succeeding. `limits` on the session options exists so tests can use small values; production uses the constants.
