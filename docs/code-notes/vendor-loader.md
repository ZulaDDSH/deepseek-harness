# vendor/loader code notes

`vendor/loader/src/config/tree.ts:EntryTree.resolve`: explicit ids may contain `:` (generated bundle rows are named `<package>:<row>`), yet `:` also joins an entry id to its parent's id (`Entry.id`). `resolve` used to split on every `:` and only walk subtrees, so a colon-bearing id in a tree store was unreachable by `resolve`, `resolveGroup`, `update` and `remove`. It now tries, per tree, the whole remaining string as a literal local id first, then each `:` split whose head is an entry with a subtree, recursing into that subtree with the rest. Literal-first is the tie-break: when a tree holds a literal id `a:b` and also an entry `a` whose subtree holds `b`, `a:b` names the literal entry. Ids without a literal match resolve exactly as before, and generated ids never contain `:`. `Entry.id` output (`parent:child`, `parent:pkg:row`) round-trips through `resolve`.

`vendor/loader/src/resolve.ts:createResolve`: the per-scope cache stored every initialization result forever, including an `undefined` after a failed helper write and a rejected helper import, so a repaired directory never produced a helper in that process. A failed result is now kept only for `RETRY_AFTER_MS` (5 s, measured with `Date.now()`), then the next call initializes again; a successful helper stays cached for good, and callers inside the window share the one pending promise, so concurrent initialization stays single-flight. A retry after a rejected helper import loads the helper from `resolve.mjs?retry=<n>`: Node caches a failed module job per URL, so re-importing the bare URL could replay the old failure after the file was repaired; the query does not change what `import.meta.resolve` anchors on, since the helper file itself is unchanged. The write-failure fallback to the Loader's own scope is unchanged and still silent, so the README keeps documenting that limit.
