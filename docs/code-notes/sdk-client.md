# sdk-client code notes

`packages/sdk/client/src/client.ts:HarnessClient::start`: the stderr reader kept every line in full and an unterminated line without limit, so one huge line (or an endless stream without a newline) grew the SDK process even though the tail was meant to be small. The reader now keeps at most `STDERR_LINE_LIMIT` characters of the current line (marking a cut line with `STDERR_TRUNCATED_MARK`) and discards the rest up to the next newline, and `appendStderr` keeps the retained tail within `STDERR_TAIL_LIMIT` lines and `STDERR_TAIL_CHARS` characters by dropping the oldest lines first. The head of a long line is kept because the first characters of a diagnostic carry the message.

`packages/sdk/client/src/client.ts:NotificationSubscriptionImpl::push`: a subscription queue grew with every matching notification while nobody read it. It now holds at most `SUBSCRIPTION_QUEUE_LIMIT` notifications. The notification that would exceed it detaches the subscription and fails it with `NotificationOverflowError`; already queued items stay drainable and the error is thrown after them, so an overflowing `Session.run()` fails visibly instead of silently losing events, and other subscriptions are untouched. A subscription that is read promptly (every run interval) never reaches the bound.

`packages/sdk/client/src/client.ts:HarnessClient::start`: the transport now reports its own limit failures (oversized input frame, stalled stdin of the child) through `onFailure`. The client fails every subscription with a `TransportClosedError` carrying the reason and starts `close()` so the child is reaped; before, only child process events failed subscriptions, so a transport failure would have left `subscription.next()` waiting forever.

## packages/sdk/client/src/client.ts:HarnessClient::request (finding 126)

A request timeout only abandoned the local waiter, so an embedder that treated it as cancellation kept paying for the runtime work. `HarnessClient::cancelSession` sends `session/cancel`; `request` also sends it, bounded by `CANCEL_TIMEOUT_MS` with every error swallowed, when `session/prompt` or `session/query` times out with a string `sessionId`, then rethrows the original `RequestTimeoutError`. Other methods are excluded on purpose: `session/wait` is an observation bound used by the subagent provider, and working-directory, `initialize` and `shutdown` do not own Session work. The cancel is awaited so the caller sees the runtime acknowledged it before the rejection, but a hung or older runtime (unknown method) cannot delay the original error beyond the bound. The cancel is session-wide: other overlapping runs on the same Session id are cancelled too, so an application that shares a Session across concurrent inputs should not rely on per-input timeouts.

`packages/sdk/client/src/client.ts:HarnessClient::request`: the timeout's abort signal is an abandonment, so the transport drops its pending entry and repeated bounded requests against a hung method retain no per-call state. It no longer implies the server keeps working until close: `session/prompt` and `session/query` timeouts follow it with `session/cancel` (see above). The class comment and this inline comment used to say there was no wire-level cancel and were removed as stale.
