# authentication-token code notes

`packages/host/authentication-token/src/index.ts:apply` (`publish`, `PENDING_API_PEER_DEADLINE_MS`, `MAX_PENDING_API_PEERS`): a `/connect` exchange creates an API Peer and signs its id into a cookie before any mux socket exists, and only a socket attachment ever disposed it. A caller holding the launch token could exchange repeatedly without attaching and grow the Peer map for the Host lifetime, and cookie expiry never removed the unused record. Each unattached Peer now carries an unref'd deadline timer. When it fires, the credential is revoked (removed from `apiPeers`) before the Peer is disposed, so a later attach with that cookie is refused. At most `MAX_PENDING_API_PEERS` unattached Peers exist at once; `publish` then returns `undefined` and `BrowserAuth::authorizeConnect` answers 503 with `Retry-After` without creating a Peer. The cap is per Host (one launch token, one owner principal), and the limit counts only unattached exchanges, so it does not restrict established sockets.

`packages/host/authentication-token/src/index.ts:apply` (`webserver/upgrade`): the deadline timer is cleared at the moment the mux upgrade is claimed (after the exact-Peer check and the active check), so a socket that attaches just before the deadline owns the Peer through the existing release path and the timer cannot dispose it afterwards. Releasing the Web scope clears every pending timer and disposes the still-unattached Peers.

`packages/host/authentication-token/src/browser-auth.ts:BrowserAuth` (`sessions`, `revoke`, `revokeAll`, `persistSessions`): browser cookies carried only an authority and timestamps, so a copied cookie stayed valid until expiry or key replacement and no single browser could be cut off (finding 114). Each minted browser cookie now carries a random `sid` and the same id is recorded, with authority and expiry, in a `sessions` map that is persisted inside the existing `client-connection/browser-session` grant record next to the secret. `revoke(sid)` moves the id into a persisted `revoked` map (kept until the cookie would have expired) and a cookie whose `sid` is revoked is refused on its next request, also after a restart. Validity is a deny-list, not an allow-list, so a cookie minted by another BrowserAuth instance on the same record (tests, a second plugin generation) still verifies; cookies from before this change have no `sid` and can only be ended by raising `sessionGeneration`. Mint stays synchronous (the response is written at once) and the record write is queued behind earlier ones; a failed write is logged and leaves the session valid until restart. `revokeAll()` and the config field `sessionGeneration` replace the signing secret and clear the map, which is the emergency global revocation: raising `sessionGeneration` and reloading the plugin invalidates every browser and API cookie, because the generation is stored in the record and a mismatch rotates the secret. API (v2) cookies are unchanged: their revocation is the Peer's socket close. Limits: there is no operator-facing screen or command in this package to list and revoke sessions, only the `BrowserAuth` methods and the generation field; a second Host process sharing the same credentials file does not see the other's revocations until it reloads.
