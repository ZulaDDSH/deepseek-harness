# authentication-token code notes

`packages/host/authentication-token/src/index.ts:apply` (`publish`, `PENDING_API_PEER_DEADLINE_MS`, `MAX_PENDING_API_PEERS`): a `/connect` exchange creates an API Peer and signs its id into a cookie before any mux socket exists, and only a socket attachment ever disposed it. A caller holding the launch token could exchange repeatedly without attaching and grow the Peer map for the Host lifetime, and cookie expiry never removed the unused record. Each unattached Peer now carries an unref'd deadline timer. When it fires, the credential is revoked (removed from `apiPeers`) before the Peer is disposed, so a later attach with that cookie is refused. At most `MAX_PENDING_API_PEERS` unattached Peers exist at once; `publish` then returns `undefined` and `BrowserAuth::authorizeConnect` answers 503 with `Retry-After` without creating a Peer. The cap is per Host (one launch token, one owner principal), and the limit counts only unattached exchanges, so it does not restrict established sockets.

`packages/host/authentication-token/src/index.ts:apply` (`webserver/upgrade`): the deadline timer is cleared at the moment the mux upgrade is claimed (after the exact-Peer check and the active check), so a socket that attaches just before the deadline owns the Peer through the existing release path and the timer cannot dispose it afterwards. Releasing the Web scope clears every pending timer and disposes the still-unattached Peers.
