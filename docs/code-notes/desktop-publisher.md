# desktop-publisher code notes

`apps/desktop-publisher/src/desktop-release-store.ts:retainDesktopRelease` (finding 172): the attempt claim (`<attempt>.lock`) was a bare directory, so a process kill, runner crash, or power loss after `mkdir` left a lock that failed every later retention of that run and attempt, along with an anonymous `.retaining-*` staging directory. The claim now carries an `owner.json` (pid, host, start time) written right after `mkdir`; `desktop-release-store.ts:claimAttempt` treats an existing claim as abandoned only when its owner is on this host and no process with that pid exists, or when it has no owner file and is older than one minute (a crash between `mkdir` and the owner write). An abandoned claim is moved aside with an atomic `rename` before being removed, so two recoverers cannot both take over, and the exclusive `mkdir` then decides the winner. A live or foreign-host owner still rejects, naming the claim path. Staging directories are named `.retaining-<attempt>-*` and are swept only after the claim is held, so they never belong to a live writer. If the destination already exists (the process died after `rename` but before reporting), the stored manifest is verified against its files and compared with the requested source and the current input files; an identical attempt returns its directory, anything else still rejects as `attempt already exists`, so a published attempt is never replaced. Limit: pid reuse after a crash can make a stale claim look live until the operator removes it.

`apps/desktop-publisher/README.md:Use this package` (finding 171): the guide linked five dispatch workflows that are not tracked in this revision (`.github/workflows` holds only ci.yml and unrelated files), so it now states that absence instead of linking them; the operator-facing guides under `apps/desktop/packaging` and `apps/desktop/publishing/ci` still link the same files and need the same correction outside this package.

`apps/desktop-publisher/src/desktop-publish-record.ts:withDesktopChannelLock` (finding 173): the lock is a directory under the machine-local release root, and `desktop-publish.ts:publishDesktopPlan` compares the channel feed against its preflight snapshot and then writes unconditionally, so two machines with unshared lock roots can interleave and the slower writer overwrites a newer feed. No fix is implemented: COS conditional writes on an observed object version are not verified for this transport, `desktopPublishCos` is restricted to the plan's object keys so a remote lock object would need a new key plus delete permission, and a lock abandoned by a crashed machine would need an operator-driven remote release. The limit is documented in the README Limitations section instead.
