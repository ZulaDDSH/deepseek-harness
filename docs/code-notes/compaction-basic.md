# compaction-basic code notes

`packages/compaction/compaction-basic/src/index.ts:BasicCompactionEngine.compactForSwitch` (finding 44): a model switch priced the new header but summarized on the conversation's committed (previous) route, so a revoked credential or exhausted quota on that route made the switch fail even though the destination could have served the summary. When no `summarizationModel` is configured and the summary call on the conversation route failed (tracked per agent by `summarize()` in `conversationSummaryFailed`), the switch now retries once with the destination route as `summaryRouteOverride`, and `compactPressure` bounds the selected range with `summaryPrefixLimit` for that destination window so the summary request fits it. The first failure is rethrown when the retry also fails, so callers and logs see the original cause; each failed attempt is atomic and commits no history. Failures that did not come from the summary call (no safe range, capacity lookup, cancellation) never trigger the retry. A configured summarization model is never replaced, and a custom `summarize()` override that bypasses the base implementation gets no fallback because it does not set the failure marker.

`packages/compaction/compaction-basic/src/index.ts:BasicCompactionEngine::summarizerWindow` (finding 117): the summary prefix bound used only the routed model's window, so a configured summarizer with a smaller window was sent a range it could not accept. When `summarizationProvider` is set, the bound for context-overflow recovery and bounded pressure compaction is now `min(routed window, summarizer window)`, with the summarizer window read through `llm.resolveModelInfo`. A summarizer whose capacity cannot be resolved keeps the previous bound instead of adding a new failure. Manual `/compact` stays unbounded, a single node larger than the bound still cannot be split, and a window no larger than `maxTokens` still disables the bound; these limits are listed in the README.

`packages/compaction/compaction-basic/src/summarizer.ts:summarizeWithLlm` (finding 119): the summary request reads `ctx.llm.stream` directly, outside the agent-loop `agent/request-error` waterfall that `llm-retry` listens to, and the retry plugin deliberately keeps raw stream consumers single-attempt because it cannot separate emitted chunks durably. The summarizer is safe to retry itself: each attempt builds a fresh `BlockAssembler`, so a partial failed summary never reaches the result, and nothing is written to the Session until a summary succeeds. It now makes up to three attempts for `TRANSPORT`, `TIMEOUT`, `SERVER` and `RATE_LIMIT` failures with a cancellable backoff (250 ms then 500 ms, or the provider's `providerRetryAfterMs` when it is at most 10 s; a longer provider wait fails immediately like the normal-mode cap in `llm-retry`). Abort during the wait rejects with the signal reason. The provider's own `retryPolicy` is not read because the adapter-level policy is only exposed to the agent loop, and retries are not logged as `llm/retry` events, so the extra attempts and their input-token cost are visible only in provider usage. Always-mode retry of permanent failures is intentionally not offered for compaction.
