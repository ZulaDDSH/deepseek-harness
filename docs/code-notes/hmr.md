# hmr code notes

`packages/client/hmr/src/client/index.ts:apply`: after a Host restart the `/plugins/events` route can answer a non-success status before the new process registers it. The browser then closes the `EventSource` permanently (no further automatic retry) and the shell-transport reader used to log and stop, so open pages kept stale plugin code (finding 38). `connect` now reopens a source whose `readyState` is CLOSED after an exponential delay (1 s doubling to 30 s, reset by the next frame), and the shell transport loop `readPageTransportEvents` retries the same way. The Host sends a full graph frame first on every new stream, so the reconnect also resynchronises the entry set. A shell transport answering 401 or 403 stops retrying, because credentials will not heal by waiting; the browser `EventSource` does not expose the status, so that path keeps retrying at the 30 s cap. In the multi-tab path only the Web Locks leader holds the connection, so retrying inside `connect` also restores the broadcasts the other tabs depend on.
