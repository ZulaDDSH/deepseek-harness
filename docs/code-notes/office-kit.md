# office-kit code notes

## Release fences saves (finding 83)

- `packages/document/office-kit/src/outputs.ts:OutputStore::reserve` - a reservation names an owner and is taken BEFORE the conversion is queued (`OfficeKit::convertTo` and `recalculate` take it before `queue.read`), because the queue wait and the conversion take seconds while the save takes milliseconds. `release(owner)` marks every open reservation of that owner released at once and waits for each to finish, so a conversion that completes after the release can no longer register an output for that owner.
- `packages/document/office-kit/src/outputs.ts:OutputStore::save` - uses the caller's reservation, or a private one when none is passed so a direct save is fenced too. `saveNow` checks the reservation and the caller signal before the write (a queued or late save writes nothing) and again after it (a save paused inside the write deletes what it wrote and rejects). A reservation taken after the release belongs to a new generation, so a later Session that reuses the owner id keeps its outputs.
- `packages/document/office-kit/src/index.ts:OfficeKit::convertTo` - finishes the reservation in a `finally`, so a failed or cancelled conversion never leaves a release waiting; `recalculate` does the same.
- Not verified: whether Session disposal aborts the tool signal that tool-office passes to `convertTo`. The reservation does not depend on it.

## Parsing runs in a kit helper, not in the Host process (finding 81)

- `packages/document/office-kit/src/index.ts:OfficeKit::runOperation` - traced `@deepseek-ai/libreoffice-kit` 0.2.3 `lib/index.js`: the conversion path runs `runWorker` (a Node `Worker` thread in the Host process that validates the OOXML archive, resolves fonts and, for WASM, converts) and then, for native engines, `runNative` / the image path, which call `spawnNative` (`child_process.spawn`) so the LibreOffice engine loads the document in a disposable helper child process. So on Windows and macOS the native parser is NOT inside the Host process; on Linux the WASM engine runs in a Worker thread of the Host process (WASM memory isolation, no native code). The kit README says the same: "A render creates a separate native process or Node worker and private profile".
- Bounds already enforced for every parse: `timeoutMs` (deadline in the helper, killed on expiry), `maxInputBytes` and the `maxSourceBytes` reservation (checked before the bytes are read), `maxOutputBytes`, and for OOXML `maxArchiveEntries` and `maxUncompressedBytes`; `tests/provider.spec.ts` "passes configured limits to the kit" proves the provider forwards them.
- Remaining limit, not fixable in this package: the helper inherits the Host's token and Job restrictions (the kit documents "inherit the caller's token and Job restrictions"), so it is not filesystem- or network-confined, and the kit exposes no memory cap or spawn wrapper. Legacy binary `.doc`/`.xls`/`.ppt` have no entry or decompression caps (only the size and time bounds). Confining the helper needs a spawn-wrapper or restricted-token option in the kit.
