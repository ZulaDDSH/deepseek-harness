# ui-directory-picker-browse code notes

`packages/client/ui-directory-picker-browse/src/client/DirectoryBrowser.tsx:separatorOf`: finding 309 showed that any backslash in the host-stamped home path selected the Windows separator, so a POSIX home whose own name contains a backslash seeded the path editor with a trailing backslash and split typed paths at it. An absolute POSIX path always starts with a slash and a native Windows path (drive, UNC, extended) never does, so a home that starts with a slash now selects the POSIX separator before the backslash test; every other home keeps the earlier answer. This stays a heuristic because the listing carries no separator: a host that reported a Windows home beginning with a slash (none does; the Host lists native paths) would be misread. The wire `separator` field named in the earlier TODO changes the Host listing contract and was not added; it remains the full fix and is a decision for the lead.

`packages/client/ui-directory-picker-browse/src/client/DirectoryBrowser.tsx:DirectoryBrowser`: finding 308 showed that when the Host confirmed a folder creation but the follow-up listing of the parent failed, the dialog showed only the listing error, so the user could read it as a failed creation and retry the same name into an existing-folder conflict. The listing failure now shows `browser.createdRelistFailed`, which says the named folder was created and carries the listing error, in all eight dictionaries registered by `packages/client/ui-directory-picker-browse/src/client/index.ts:apply` (non-English wordings are UNVERIFIED by a native speaker). The created folder is not selected automatically: selecting it would launch another listing whose success clears the message; the user continues by navigating (a crumb or Home) which relists, and the created folder appears in the list. A dedicated retry button was not added.
