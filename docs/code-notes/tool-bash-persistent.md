# tool-bash-persistent code notes

## stdin_read fallback keeps the session open (finding 130)

- `packages/shell/tool-bash-persistent/src/index.ts:executeCommand` (the `result.waitReason === 'stdin_read'` branch) - when the shell reads stdin again without the end marker, the call returns the captured partial output and leaves the shell open. This covers `exec`, an interrupt and an interactive foreground child alike, and the backend cannot tell a returned shell prompt from a child's input wait. The existing tests assert the retention deliberately (`tests/tools.spec.ts` 'handles inferred idle, stdin_read fallback, shell exit, clipping, and cleanup'; the pwsh twin states the same in its test comment), and resetting the shell on every `stdin_read` would discard state after an ordinary `exec` or interrupt. The consequence stays: an interactive child that is still reading consumes the next call's command as input until that call reaches `timeoutMs` and resets the shell. It is documented as a limitation rather than changed; a structured waiting-for-input state or an input operation would need a provider signal that separates a child's read from the shell's own prompt, which only the proven stdin-wait tier provides.
