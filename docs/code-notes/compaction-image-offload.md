# compaction-image-offload code notes

`packages/compaction/compaction-image-offload/src/projection.ts:imageRestoreProjection` (finding 118): an `image/offload` mark was permanent, so a temporary Files outage, a short stay on a small-budget route or a compaction that lowered the image total left the placeholders in every later request. Recording the route in the offload event would not help: the projection is a pure fold of the log and has no current route, so it cannot decide to drop a mark when the route changes. The smallest sound reversal is a second durable event, `image/restore`, with the same `{ targets: [{ seq, imageIndexes }] }` shape as `image/offload`. It clears the `offloaded` key on exactly the named occurrences (the key is deleted, never written as `false`), keeps message identity, and throws at append and at replay when a named occurrence is missing or is not currently offloaded, so a restore can never be applied twice or to an image that was never marked. It is a separate event type, not a flag on `image/offload`, so a consumer that folds `image/offload` targets (the token meter) cannot silently read a restore as an offload. A reader that knows `image/offload` but not `image/restore` refuses the log as an unknown required event instead of misreading it. Because the Session format discriminator already refuses unknown non-ignorable events, this is a same-version addition, like `image/offload` itself (`docs/persistence-changes/2026-09-14-image-offload.md`), not a format bump.

`packages/compaction/compaction-image-offload/src/image-offload.ts:restoreOffloadedImages` (finding 118): the explicit restore control. It appends one `image/restore` selecting every currently offloaded occurrence on the current surface nodes, or on the given nodes, and returns false when nothing is offloaded. Nothing calls it automatically: restoring on every request or route change would make a route that is still too small fail, offload and restore again on every turn, and a plugin cannot tell a transient budget from a lasting one. The caller (a command, an RPC or an operator script) decides when the cause is gone. If the route still rejects the images, the existing `agent/request-error` listener offloads them again, so a wrong restore costs one failed attempt and no data. The user-facing trigger is `/restore-images` (below).

`packages/compaction/compaction-image-offload/src/index.ts:apply` (finding 118): registers the `/restore-images` command. The package takes `dsh-commands` as a peer dependency and `dsh-brand` as a runtime dependency for this alone. The command is bound through `ctx.inject(['commands'], ...)`, not the static `inject` list, because `commands` is optional: a composition with the offload plugin but no command runtime (the SDK-minimal bundle) must still load the recovery listeners. The handler restores every offloaded occurrence on the invoking agent's session through `restoreOffloadedImages` and reports "restored" or "nothing was offloaded"; it takes no arguments and rejects any, because a partial restore by sequence number is not something a human can name. In `packages/compaction/compaction-image-offload/src/index.ts:apply` the registration sits in `inner.effect`, so it unregisters with the plugin or the command runtime. The restore is itself a logged `image/restore` event, next to the executor's `command/run` and `command/done` pair. The result text says the images are sent again from the next request and that a route still over its budget offloads them again, so the model-visible effect is stated to the user, not hidden.

`packages/compaction/compaction-image-offload/src/project-message.ts:setMessageImagesOffloaded`: one walk serves both directions. Offload requires each selected occurrence to be unmarked and restore requires it to be marked, which is what makes the projections atomic and non-repeatable.
