# tool-fs code notes

`packages/fs/tool-fs/src/edit.ts:parseEditArgs` (finding 23, issue #126): `edit` could only replace a non-empty literal, so appending to a file needed a unique anchor and an empty file could not be edited at all; agents wrote throwaway scripts instead. The tool now takes `append: true`, which adds `new_string` verbatim to the end of an existing file; `old_string` must then be empty (the schema still requires the field, so the model sends an empty string, which keeps the `file_path`, `old_string`, `new_string` field order the argument streamer relies on), and `replace_all` is rejected as meaningless. Without `append`, an empty `old_string` is still rejected, so a model that forgot the anchor does not silently append. The request reaches the backend as `FsEditRequest.append`, with `oldString` fixed to the empty string, so the same guard, lock, sandbox, line-ending and atomic-write path serves both modes. No newline is inserted: the model owns the separator, because inserting one would change files that end without a newline. `append` is advertised in the schema, so it changes the tool-definition prefix once. A missing file still fails as stale (`edit` never creates files; `write` does), and an append onto an empty file is the supported way to fill it.

`packages/fs/tool-fs/src/edit.ts:formatEditOutput`: an append reports "has been appended to" so the model can tell it from a replacement. `presentCall` shows the appended text as an added block (`oldText: null`).
