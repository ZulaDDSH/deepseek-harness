# mcp-client code notes

`packages/mcp/mcp-client/src/connection.ts:startConnection` (finding 77): the SDK `onChanged` callback called `refreshTools()` for every `notifications/tools/list_changed`, and each call queued its own sync on `syncChain`. A server that notified faster than `tools/list` completed grew the promise queue without bound and made the Host re-list and re-register the whole tool set long after the burst. `refreshTools` now runs inside one generation closure with an active flag and a pending flag: a notification during an active refresh only sets the pending flag, and when the active refresh finishes at most one rerun starts, so a burst costs one active listing plus one rerun and the rerun reads the server's latest list. Reruns are spaced at least `REFRESH_MIN_INTERVAL_MS` (250 ms) apart from the previous start, so a server that notifies continuously is bounded to about four listings a second instead of the listing rate. The pause ends as soon as the generation closes (`McpGeneration` lifetime abort) and the loop stops when the generation is no longer current, so a replaced or disposed generation leaves nothing queued. The state lives per `connectGeneration` call, so a reconnect starts from a clean flag pair and an older generation's loop cannot rerun against the new client. The initial sync after connect still goes through `enqueueSync` directly and is not counted in the coalescing state; a notification that arrives during it coalesces behind the first refresh it starts.

`packages/mcp/mcp-client/src/connection.ts:boundedResourceRead` (finding 78): `resources/read` returned the SDK's parsed result straight to the resource tools, so a large text body or base64 `blob` was held in full and then rendered into model history with no package-level limit; blob payloads were dropped only at JSON rendering time, after the base64 was already in memory. `boundedResourceRead` now totals the UTF-8 bytes of every `text` field and the length of every `blob` field in `contents` and rejects the whole read with `McpLocalError` code `MCP_RESOURCE_TOO_LARGE` (a local error so `mcpRequestError` does not rewrap it as `MCP_REQUEST_FAILED`) when the total passes `MAX_RESOURCE_READ_BYTES` (8 MiB, a fixed constant, not configuration). The limit applies to the resource data the model-facing renderer would otherwise carry, so a rejected blob never reaches the renderer, and the error names the URI and sizes, never the content. The bridge cannot stop the bytes arriving: the MCP SDK parses the JSON-RPC frame before this code sees it, and the transport has no per-response byte hook here, so peak memory while the SDK parses one oversized response is not bounded by this check. It bounds what the bridge forwards, retains in tool values and renders. Listing results (`resources/list`, `resources/templates/list`) are not measured: they are paged by cursor and carry only descriptors.

## Tool-call result byte budget (finding 145)

- `packages/mcp/mcp-client/src/tools.ts:syncTools` (the `call` closure) - the result of `client.callTool` is measured by `resultBytes` before output-schema validation, error redaction and conversion, and one over `MAX_TOOL_RESULT_BYTES` (8 MiB, the same figure as `connection.ts:MAX_RESOURCE_READ_BYTES`) is rejected as `MCP_INVALID_RESULT` with the measured size. The walk counts UTF-8 text bytes, image/blob string length and structured values, and stops as soon as the limit is crossed, so rejecting costs at most limit-sized work.
- Limit: the SDK client has already received and parsed the whole JSON-RPC message when this runs, so the check bounds validation, conversion, image projection and retention but not the transient receive/parse memory; bounding that needs a limit inside the SDK's stdio and HTTP transports, which this bridge does not own. Aggregate in-flight budgeting across concurrent calls is not added.

## Non-object tool arguments (finding 369)

- `packages/mcp/mcp-client/src/tools.ts:createExecutor` - arguments that are not a JSON object (null, a primitive, malformed JSON preserved as its raw string by the batch scheduler, or an array) are rejected with `ToolArgsError` before `options.call`, so no `tools/call` reaches a server whose parameters are all optional; a valid `{}` still calls the server. `packages/experimental/browser-use-stagehand-native/src/index.ts` validates `exec.arguments` against the zod input unchanged, so it no longer reads non-objects as `{}` before acquiring a browser.

## Host-operation error redaction (finding 370)

- `packages/mcp/mcp-client/src/connection.ts:startConnection` (the registered `call`) - when `expandTemplates` is on, an `isError` result from the human-operations call is reduced to its redacted text parts, like the model-facing bridge in `packages/mcp/mcp-client/src/tools.ts:syncTools`; successful results are returned unchanged. The same closure supplies `McpHumanOperations.redact` (`human-operations.ts:McpHumanOperations`), which is the identity when templates are not expanded.
- `packages/client/ui-memory-workspace/src/store.ts:excerpt` - the 300-character excerpt copied into Memorix rejection and missing-acknowledgement errors is redacted through `provider.redact` before it is truncated, so a secret cut by the limit is not partially exposed; a provider without `redact` keeps the raw excerpt.
