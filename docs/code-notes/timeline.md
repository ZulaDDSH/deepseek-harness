# Timeline code notes

- `packages/experimental/timeline/src/checkpoint.ts:Checkpoint::toJson` (finding 166): a task's remaining-time estimate and its serial or parallel mode are exported as optional `remaining` and `mode` task fields, written only when they differ from the import defaults (no estimate, serial). The format stays version 1 because the new fields are optional: a file without them restores exactly as before, and a file that uses them is rejected by an older strict reader instead of silently losing the estimate. Groups derive `remaining` from their children, so only leaves export `remaining`; `mode` is exported for groups as well because it selects how child durations combine. Done tasks always restore with zero remaining and omit the field.

- `packages/experimental/timeline/src/storage.ts:TimelineStorage::control` (finding 167): a pending request for overlapping work with the opposite action is no longer returned as a silent duplicate with `dispatch: false`. The earlier request may already have reached the agent and cannot be recalled, so the new request is refused with an actionable conflict that tells the user to wait for the confirmation or for the two minute wait to elapse. Same-action duplicates still return the existing request, and a repeat of the same request identity stays idempotent. Superseding with a new ordered identity is not implemented because the agent has no cancel path for a request it has already read.
- `packages/experimental/timeline/src/storage.ts:TimelineStorage::control` (finding 168): when the flush that follows appending the control record fails, the request id is remembered in `undispatched`. The client never sent its prompt in that case, so the next request for the same action and overlapping work re-flushes the buffered record, and once that succeeds it returns the existing request with `dispatch: true` instead of `dispatch: false`. The set lives in memory only. After a restart a record that was persisted but never sent waits out the two minute pending window like any unconfirmed request, then can be retried; that limit is documented in the README.

- `packages/experimental/timeline/src/controls.ts:oldestResolvedAnnotation` (finding 170): at the 512 discussion cap a new discussion or control request evicts the oldest resolved annotation (answered discussion or control with a recorded outcome) from the view instead of failing. Open discussions and pending controls are never evicted, so a full set of unresolved items still rejects with the capacity error. The evicted record stays in the Session log; only the live view drops it, matching how expired reports leave the view. Both `TimelineStorage::append` (admission check) and `applyAnnotation` in `projection.ts` use this one helper so live admission and replay agree. Import still rejects when the combined count exceeds the cap. A capacity indicator in the client is not added.
- `packages/experimental/timeline/src/projection.ts:foldRecord` report branch (finding 169): not changed. Each report event copies the retained list and filters it for duplicates and expiry, and the state is an immutable value that is spread on every fold, so an incremental index would need a mutable side structure shared between previous and next states, plus a paged client protocol, which is a redesign of the projection and client sync. The cost is documented in the README Dev Note; the retained window is bounded at 50,400 reports and only reaches that size at a one minute cadence.
