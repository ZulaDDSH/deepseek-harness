# remote-access code notes

## packages/api/remote-access/src/index.ts:RemoteAccessService::changes

`packages/api/remote-access/src/index.ts:RemoteAccessService::changes`: Finding 135. The follower set behind `invalidate()` was private, so a business stream that filters its own frames through `allows()` (Workspace follow) could not learn that a grant changed and kept a revoked or not-yet-granted entry on screen until an unrelated registry event arrived. `changes(principal, signal)` is a plain (non-Remote) async iterable that registers an `AccessFollower` on its first pull and yields once per coalesced invalidation of that principal; it ends when `signal` aborts or the service unloads. Like `follow()`, the follower is registered synchronously by the first `next()`, so a caller that starts pulling before it reads its own baseline cannot miss a change. The owner never changes, so for the owner the stream only waits for cancellation. `follow()` keeps its own follower use because it must read its baseline after registering.

packages/api/remote-access/src/index.ts:RemoteAccessService::grantsFor (finding 347): the snapshot searched the seen resources and rescanned every binding for each resource and each candidate action, and `follow` diffed the old and new grant lists with nested linear searches, so a principal with many bound resources cost at least quadratic work per snapshot, repeated for every follower on every invalidation. Bindings are now grouped by resource identity once per computation, in first-binding order, and each resource evaluates only its own group, so the allowed actions, the order of grants, the order of bindings within a resource (which decides the first refusal and the condition call order) and the `decide()` agreement are unchanged. `follow` indexes the previous grants by resource identity and emits upserts in the new order, then removals in the old order, as before. `AccessFollower::key` holds the principal's canonical JSON so `invalidate` stops re-serializing every follower's principal.
