# ui-memory-workspace code notes

`packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation::withProject` (findings 186, 188): the Memorix server holds one project binding per MCP connection. Automation cached "this workspace is already bound" per `McpHumanOperations` object, but the model-facing `memorix_session_start` tool can change that binding without telling the cache, and a reconnect replaces the server process while the operations object stays the same. Rebinding before every operation is not an option: `memorix_session_start` opens a session row and auto-closes the previous active one, so a bind per document chunk would flood the sessions table. The cache now stores the project id parsed from the bind reply (`Project: <name> (<id>)`). Every store compares the project Memorix acknowledges (`Project: <id>` in the store reply) with that id; a mismatch drops the cache entry, fails that write with a message naming both projects and retries once after a fresh bind. Any other failure of a bound operation also drops the cache entry, and one retry runs when the server's own error asks for `memorix_session_start` (an unbound server after a restart). Search results carry `obs:<id>@<project>`; rows from another project than the bound one are dropped. The mismatch is detected after the write, so the first write after an external switch can still land in the other project and stays there; closing that window needs request-scoped project selection or a connection generation from `packages/mcp/mcp-client/src/human-operations.ts` and is outside this package. A bind reply without a recognizable project line (older servers) disables the comparison and keeps the old cache-only behaviour.

`packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation::recallFirst` (finding 195): the three-second first-message budget only raced the recall promise, so a recall that was queued behind another Memorix operation still ran its search later, after the chat had already fallen back to recent notes, and a burst of expired recalls delayed saves and imports. `recallFirst` now owns one `AbortController` that aborts when the budget expires; `recallNotes` passes it into the exclusive queue entry, which returns without binding or searching when the signal is already aborted, and into `search` as the caller signal so a search that already started is cancelled. The separate search timeout still starts when the search actually runs. An aborted recall is not reported as a failure because the fallback path already reported the expiry.

`packages/client/ui-memory-workspace/src/automation.ts:SessionTurns::begin` (finding 194): every admitted user message called `begin`, which replaced the stored prompt, so a steering message dropped the original request from the turn digest. `begin` now appends to the messages of the open turn; `finish` and the new `discard` close it. `discard` runs on every `turn/end` that is not `completed`, otherwise an interrupted turn's prompts would be merged into the next turn once messages accumulate. The assistant outcome is still cleared on every admitted message because an answer written before a steer no longer describes the turn. The prompt budget is `PROMPT_CHARACTERS * 2`, shared evenly between the messages (at least 40 characters each, clipped with an ellipsis), joined with ` | Then: `, so the original request and every steer stay visible and truncation is deterministic. The turn title still uses the first 70 characters, which belong to the original request.

`packages/client/ui-memory-workspace/src/client/MemoryPage.tsx:upload` (finding 193): the panel read each selected file with `file.arrayBuffer()` and base64-encoded it before the Host could compare it with `maxDocumentBytes`, so an accidentally selected multi-gigabyte file was fully allocated in the renderer first. `MemoryWorkspace::status` now returns the effective `maxDocumentBytes`, and `upload` compares `File.size` with it before any read; an oversized file is skipped with a localized message naming the file and the limit, and the remaining files still upload. The status is loaded when the page mounts; while it is unavailable (failed status call) the panel has no limit and the Host check remains the only guard. The accepted file is still read whole and sent as one base64 string (at most `ceil(maxDocumentBytes / 3) * 4` characters), because the Remote protocol has no chunked upload; a bounded streaming upload is not implemented.

`packages/client/ui-memory-workspace/src/types.ts:MemoryStatus` (finding 193): carries `maxDocumentBytes`, the Host's effective upload limit, so the panel can refuse an oversized file before reading it. `packages/client/ui-memory-workspace/src/index.ts:MemoryWorkspace::status` fills it from the validated `maxDocumentBytes` config value.

`packages/client/ui-memory-workspace/src/index.ts:MemoryWorkspace::graph` (finding 189): the endpoint took no request signal and its Graphify subprocess only saw the service lifetime, so a client that timed out or unmounted left the rebuild running and every later open or refresh queued another rebuild behind it. `graph` now declares a trailing `AbortSignal`, which the gateway fills with the caller's lifetime (and which also removes the 30 second unary client deadline, so the Host owns the limit). The queued entry starts with `throwIfAborted`, so a rebuild whose caller is gone is skipped without spawning Graphify. `loadGraph` combines the caller signal, the service lifetime and `AbortSignal.timeout(graphTimeoutMs)` into the signal handed to `runNativeCommand`, whose `execFile` kills the child when it aborts; an expiry that is not the caller's own abort is reported as a Graphify timeout naming `graphTimeoutMs`. `MemoryPage` aborts the in-flight graph request when the Context graph tab closes, the panel unmounts or Refresh starts another request. Simultaneous equivalent rebuilds are not coalesced: callers have independent lifetimes, so sharing one run would let the first caller's cancellation cancel the others. Process cleanup is confirmed only as far as `execFile` reports the kill; a child that ignores SIGTERM is not escalated.

`scripts/graphify-native.py:memorix_graph` (findings 190, 192, 187): the adapter selected every active observation whose topic key began with `document:`, fetched all narratives, and raised on the first row that was not an importer chunk, so one unrelated memory such as `document:design-notes` or one damaged chunk kept the whole graph from building, and the number and total size of stored documents was unbounded before the Host's output-size check ran. `document_rows` now selects only importer-shaped topics (`document:` plus 64 hexadecimal characters and `:part:`) and counts distinct documents and their summed narrative bytes before fetching any narrative; `memorix_graph` raises `ValueError` naming the limit when the count passes `--max-documents` or the bytes pass `--max-source-bytes` (the Host passes `maxGraphDocuments` and `maxGraphSourceBytes`; the direct `--memorix-database` prefix uses the module defaults). `group_chunks` validates each row on its own: a row whose title or part number is damaged is left out and reported on stderr as `graphify-native skipped: observation <id> (<topic key>): <reason>`, which the Host returns as `MemoryGraph.skipped`; the other documents still build, and the document owning a damaged chunk stays out because its set is incomplete. Chunks are grouped by project, file hash and the part total in their title, so after a re-import with a different `chunkCharacters` the stale higher-numbered parts (old total) never mix with the new complete set (new total); at most one total can be complete for a hash because part numbers are unique topic keys. At most 20 skipped rows are printed, then one `N more damaged chunks` line, because the Host's `execFile` buffer is 1 MiB and a store full of damaged chunks must not turn a graph build into a buffer error. `packages/client/ui-memory-workspace/src/index.ts:MemoryWorkspace::loadGraph` passes the two Config limits and collects the `graphify-native skipped: ` stderr lines into `MemoryGraph.skipped`, which `MemoryPage.tsx:MemoryPage` lists under the viewer.

`packages/client/ui-memory-workspace/src/index.ts:MemoryWorkspace::retireStaleParts` (finding 187): re-importing a file with a smaller `chunkCharacters` left the old higher-numbered parts active under their own topic keys. After every chunk of a new import is stored and verified, `retireStaleParts` pages the file's `document:<hash>:part:` rows, selects the active ones whose project is the acknowledged project and whose part number is above the new total, and archives them with `memorix_resolve` through `MemoryAutomation::archive` (exclusive, bound). `memorix_resolve` only touches ids in the bound project, so a wrong binding archives nothing; the helper re-reads the rows and reports `Stale document parts remain active` in `result.error` when any are still active. An interrupted replacement archives nothing, so the older complete set stays valid until the new set is complete (the adapter groups by part total and never mixes the two).

`packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation::withProject` (finding 276): the chat-memory switch was read only when an automatic save or recall was admitted, so turning it off while a save waited on provider acquisition or workspace binding still wrote the chat record afterward, and a recall in flight still returned its notes into the prompt. Automatic saves and searches now pass `automatic` so `withProject` re-reads the switch before and after binding and throws `MemoryDisabled`, `MemoryAutomation::save` and `recallNotes` re-read it after acquiring the provider, `recallNotes`, `recentNotes` and `lookup` discard their text when it is off, and the `system-prompt/assemble` handler re-reads it after awaiting the pending recall. `MemoryDisabled` is not a failure and is never reported. A Memorix call already dispatched when the switch flips cannot be retracted, so a write that was sent still lands; the fence only stops work that has not yet been dispatched and the insertion of recalled context.

packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation (finding 371): the `system-prompt/assemble` handler registered a one-shot abort listener on the turn signal for every assembly and removed it only when the signal aborted, so a long multi-step turn kept one listener and closure per step after recall had finished. The handler now registers a named listener and removes it as soon as the recall promise settles, and an already-aborted signal registers nothing.

packages/client/ui-memory-workspace/src/automation.ts:workspaceEntity (findings 372, 373): the entity name combined the basename of the supplied path with an 8-hex hash of the lexically resolved path lower-cased on Windows, so `C:\Work\Project` and `C:\Work\project` (same hash, different basename), `/work/project/..` (basename `..`) and a symbolic-link alias each named a different entity and split one workspace's memories, while two sibling folders differing only in case on a case-sensitive Windows tree shared one entity, and any two folders with one basename could collide in 32 bits. The identity is now derived from `canonicalWorkspace`, the `realpathSync.native` of the resolved path (the filesystem's own spelling and case, aliases followed), falling back to the resolved path unchanged when the folder does not exist, and nothing is case-folded: the basename and a 16-hex SHA-256 prefix both come from that canonical path, so equivalent spellings agree and case-distinct folders differ. A folder that does not exist keeps its spelling, so a case variant of a missing path still names a separate entity rather than risking a shared one. `workspaceHash` is unchanged because it also names the non-Git Memorix project folder under `memorix-roots`; changing it would re-home every stored project. Notes saved before this change live under the old 8-hex names: `legacyWorkspaceEntities` derives the old name for the supplied spelling and for the canonical path, recall reads them as a secondary match (`MemoryAutomation::search`, `MemoryAutomation::recent`), and every new save uses only the new name. Old names keep their old weakness: a legacy row written by one of two case-distinct sibling folders still matches both, and a legacy name written under a third spelling of the folder is not found. The fallback recent-notes query still does not filter by project.

`packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation.storeIn`: when the acknowledged project differs from the bound one, the write has already landed in the wrong project, so the observation is archived through `memorix_resolve` (status `archived`, while the server is still bound to that wrong project) before the mismatch is thrown and the single rebind retry runs; a failing archive is ignored so the retry still happens. `REBIND` only matches the server's "Cannot ... yet." refusal and the "call memorix_session_start" hint, not any message that merely mentions `projectRoot` or the tool name, so an unrelated failure is not retried (and a retry never repeats a write that was accepted).
