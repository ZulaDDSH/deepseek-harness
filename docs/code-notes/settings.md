# settings code notes

`packages/settings/settings/src/index.ts:SettingsForms::importLegacyDocument`: the legacy `settings.yaml` used to be renamed to `settings.yaml.imported` before it was parsed or applied, so a crash, read error or parse error after the rename left the settings unapplied with no retry, and a later legacy file renamed onto the same name replaced the earlier recovery copy (findings 115, 116). The document is now read and parsed first and applied section by section while still at its original name; applying a section writes the same values every time, so an interrupted import simply repeats on the next start. Only after every section has been attempted is the source moved aside, by copying it to the first unused `settings.yaml.imported[.N]` with `COPYFILE_EXCL` (exclusive creation, so no existing recovery copy can be replaced even by a concurrent import) and then removing the original. A section the running composition rejects is still logged and remains only in the recovery copy; the log line names the copy. An unparsable document stays in place and is reported on every start until the operator fixes or removes it. The copy-then-remove step is not atomic: a crash between the two leaves both files, and the next start imports again (idempotent) and writes a further numbered copy.

`packages/settings/settings/src/index.ts:keepRecoveryCopy`: exclusive-create (`COPYFILE_EXCL`) on `settings.yaml.imported`, then `.imported.1`, `.imported.2`, and so on, so a repeated legacy import never replaces an earlier recovery copy that may hold the only record of rejected sections. There is no retention limit; the operator deletes copies. The old `importLegacyDocument` docblock claimed the document was renamed before the first write; that behaviour is gone (findings 115, 116).
