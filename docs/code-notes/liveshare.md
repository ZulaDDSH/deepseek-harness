# liveshare code notes

`packages/experimental/liveshare/src/host/viewer-access-policy.ts:VIEWER_SOURCE_WRITE_ROLE`: `fileUploads/upload` used to sit in the session read role, so attachment upload followed visibility alone and a viewer on a share the host could not drive (no established tier, or no confined access layer) or on a revoked fork could still stage files into the owner's attachment store, which is a write to the owner's disk. It is now a write action of `VIEWER_SOURCE_WRITE_ROLE` (refused while `sourceWriteRefusal` refuses prompt and stop) and of `VIEWER_CHILD_ROLE` (refused on a revoked fork through `childWriteRefusal`), and `packages/experimental/liveshare/src/endpoint-classification.ts:VIEWER_ENDPOINT_CLASSES` classifies it `reader-session-input`. The view tier still attaches files, because it still prompts; the write tier decides nothing here. A reader cannot attach to another reader's fork or a Session it cannot see, as before. The raw route `/api/session/uploadFileBinary` registered by `packages/client/file-upload/src/index.ts:FileUploads` is an exact Fetch route, and `packages/client/connection/src/rpc-host.ts:createSharedFetchHandler` answers 403 to every non-owner principal before the route runs, so a `share-viewer` Peer never reaches it; covered by `packages/experimental/liveshare/tests/viewer-access-policy.spec.ts`.

`packages/experimental/liveshare/src/endpoint-classification.ts:VIEWER_ENDPOINT_CLASSES`: `toolResults/watch` was classified `reader-session-read` and listed in the session read role, so a viewer could stream the raw value of any retained tool result of a visible Session. The viewer's trajectory view shows tool output after the tool-output projection, while this Remote returns the unprojected value, so the raw stream leaked what the projection withholds. It is now `owner-only`: no viewer role lists it and `POLICY_DECIDED_ACTIONS` no longer includes it. The service namespace `toolResults` is already in `packages/experimental/liveshare/src/host/shareable-catalog.ts:EXCLUDED_SHARE_NAMESPACES`, so a plugin declaration cannot offer it either. The viewer page's watcher (`packages/client/ui-trajectory/src/client/watch-tool-result.ts:createToolResultWatcher`) already publishes `undefined` when the stream fails, so a refused watch shows the result as unavailable.

`packages/experimental/liveshare/src/endpoint-classification.ts:VIEWER_ENDPOINT_CLASSES`: `sessionFeedback/sharing` is `owner-only`; it reveals the Host's telemetry policy and collector origin and no viewer role needs it. A viewer's feedback dialog falls back to the generic disclosure when the call is refused.

`packages/experimental/liveshare/src/host/shared-tools.ts:sharedEditArguments` (finding 23, issue #126): the bounded edit body replaces the deployment `edit` execution on viewer-started shared turns and on forks, so it re-runs that tool's argument checks, and it rejected every empty `old_string`. The shipped `edit` now also accepts `append: true` (empty `old_string`, non-empty `new_string`, no `replace_all`), which would have been refused only on shared turns. `sharedEditArguments` accepts the same form and returns `append: true`; `fork-enforcement.ts` passes it to `fs.editText` as `{ append: true }` only when set, so replacement calls reach the seam unchanged. The path confinement, write-gate and policy checks around `editText` are untouched, so an append is confined and gated exactly like a replacement. An empty `old_string` without `append` is still refused.
