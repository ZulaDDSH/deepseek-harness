# gateway code notes

`packages/api/gateway/src/stream-server.ts:RemoteStreamMuxConnection::openStream`: a connection used to admit any number of distinct logical stream ids, each with its own handler and inbox. It now refuses an `open` once `MAX_STREAMS_PER_CONNECTION` streams are active, answering that stream id with a `gateway/protocol` error frame and leaving the socket and the other streams alone. The refused id is not registered, so its later `item`, `end` and `cancel` frames are dropped like frames for a finished stream.

`packages/api/gateway/src/stream-server.ts:ConnectionInboxBudget`: `streamInboxBytes` bounds one stream, so many streams could still buffer without limit. All inboxes of one connection now charge a shared budget of `max(MAX_CONNECTION_INBOX_BYTES, streamInboxBytes)` bytes; an item that would exceed it fails only its own stream with `gateway/uplink-overflow`. The budget is released when an item is read, or when the inbox fails or returns, so cancellation and disconnect leave it at zero.

`packages/api/gateway/src/index.ts:RemoteEventQueue`: the per-client Remote-event queue had no limit, so a Client or intermediary that read slower than the Host produced notifications retained an ever-growing backlog while the stream stayed connected. `push` now counts the frame against `MAX_REMOTE_EVENT_QUEUE_FRAMES` (4096) and `MAX_REMOTE_EVENT_QUEUE_BYTES` (8 MiB of JSON text, measured once per frame object and cached because one broadcast frame is shared by every client). The frame that would exceed either budget does not drop a single frame: the whole backlog is discarded and the stream fails with `gateway/event-backlog`, which reaches the Client as a stream error so the Client reconnects. Nothing pending is lost silently, because a new Client generation is handed every still-pending scoped waterfall on connect (`TypertGatewayService::openRemoteEvents`), and replaceable invalidations are refetched by the reconnecting Client. A coalescing scheme was not added: the notifications carry payloads that are not safe to merge generically.

`packages/api/gateway/src/index.ts:RemoteEventQueue.push`: a single frame larger than `MAX_REMOTE_EVENT_QUEUE_BYTES` used to fail the stream even on an empty queue, and a reconnect that replays that frame as a pending waterfall hit the same limit again. `push` now always admits a frame while the queue is empty, so one oversized frame is delivered and the memory held stays bounded by that single frame; the budgets only reject a frame that arrives behind queued frames. The connect-time burst is unchanged: `openRemoteEvents` pushes every still-pending scoped waterfall synchronously before the consumer reads, so more than `MAX_REMOTE_EVENT_QUEUE_FRAMES` pending events, or pending frames totalling more than `MAX_REMOTE_EVENT_QUEUE_BYTES` beyond the first, fail the new stream with `gateway/event-backlog` and the Client reconnects into the same burst until some pending events settle or are cancelled. This is deliberate: pending events are bounded by the Host answering or cancelling them, and exempting the connect burst would reintroduce an unbounded per-client backlog.
