# file-upload code notes

`packages/client/file-upload/src/index.ts:FileUploads.assertSessionQuota`: receipts stayed staged until a prompt sent them, so one Session (and any reader allowed `fileUploads/upload` on it, finding 30) could accumulate unlimited receipts. Each Session may hold at most `MAX_STAGED_PER_SESSION` (100) receipts and `MAX_STAGED_BYTES_PER_SESSION` (4 GiB) bytes; the check runs before storing and `stage` re-checks with the real size, so a concurrent burst can overshoot by the in-flight uploads only, which the store-wide quota in attachment-local bounds. Staged receipt accounting is memory only; the bytes already written to the attachment store are not removed when a receipt is refused, because content-addressed objects can be shared.

The browser has no call that retires a receipt when the user removes a draft file, so removed-but-unsent uploads keep counting towards the Session cap until a prompt uses them or the Session is disposed; the refusal message says so.

`packages/client/file-upload/src/client/runtime.ts:workerTransport`: the Blob URL is revoked in a `finally` around Worker construction and a synchronous `postMessage` failure (locked or untransferable stream) now runs `finish`, so the Worker is terminated and the abort listener detached; both failures reject the returned Promise instead of throwing from `post` (finding 350).

`packages/client/file-upload/src/index.ts:FileUploads.assertSessionQuota`: receipts not bound to a prompt expire `UNBOUND_RECEIPT_TTL_MS` (24 h) after staging and are pruned lazily whenever the Session's quota is checked, so abandoned drafts stop counting against the 100-receipt cap; prompt-bound receipts are never expired here and are still retired by `retire`. The map was already bounded by the quota, so finding 357's unbounded growth was overstated; no browser call to release a receipt exists, and a draft idle for more than a day must be re-uploaded (finding 357).

`packages/client/file-upload/src/index.ts:FileUploads.store`: the pre-save quota check now counts the incoming bytes when they are known, which is the decoded size bound of an encoded `upload` (`floor(length * 3 / 4)`), so an upload that cannot fit is refused before anything is written; streamed uploads and images only learn their size while storing, so they still rely on the re-check in `stage`. The attachments service has no delete or release call and stored objects are content-addressed and may be shared, so a file that loses the race at `stage` and a receipt pruned by the unbound-receipt TTL both leave their stored bytes to the store-wide quota in attachment-local (review finding on orphaned uploads).
