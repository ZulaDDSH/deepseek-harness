# llm-pi-ai code notes

## Multi-account Claude: route aliases

- `packages/llm/llm-pi-ai/src/config.ts:PiAiProviderProfile.base` — a route key normally equals the installed pi-ai catalog provider id, so `anthropic` could hold one sign-in only. `base` names the catalog provider a route is a second account of (for example route `claude-work` with `base: 'anthropic'`). Credentials stay keyed by the route key, so every alias has its own `llm-pi-ai/<route>` record and its own OAuth login; models, auth methods and dispatch come from the base provider.
- `packages/llm/llm-pi-ai/src/config.ts:resolveProfiles` — rejects a `base` that is not an installed catalog provider, and any route key that is itself an installed provider id (it already owns that provider's flow and record). The error is thrown in both strict and deferred modes because it is a configuration mistake, not a catalog-upgrade diagnostic.
- `packages/llm/llm-pi-ai/src/catalog.ts:resolveRouteModels` — catalog lookups (default models, provider endpoint) use `request.base ?? provider`; the materialized models still carry the route key as `provider`, so selectors and requests address the alias, not the base.
- `packages/llm/llm-pi-ai/src/provider.ts:buildProvider` — looks the catalog provider up by `spec.base ?? spec.provider` and keeps `id: spec.provider`, so pi-ai resolves credentials under the alias route.
- `packages/llm/llm-pi-ai/src/login.ts:registerPiAiFlows` and `src/index.ts` — sign-in flows are registered per route: catalog ids at mount, alias routes whenever the `providers` profiles change, and disposed when an alias is removed.
- `packages/llm/llm-pi-ai/src/claude-quota.ts:createClaudeQuotaSource` — quota is per account: one source and one usage store per route whose base is `anthropic`, so rate-limit headers from one account never show on another's meter.
- `packages/llm/llm-pi-ai/src/claude-quota.ts:readSubscriptionWindows` — `builtinModels` only knows stock provider ids, so an alias route registers a copy of the Anthropic provider under its own id before `getAuth`, otherwise the usage fetch for an alias account could never find its credential.
- `packages/llm/llm-pi-ai/src/index.ts:directoryEntries` — alias routes are listed `declared: false` (their catalog is the base's), and model discovery resolves the base provider's catalog for them.
- `packages/llm/llm-pi-ai/src/index.ts:apply` — the volatile-update handler runs each sync step in its own try block so a route conflict cannot leave alias flows or quota sources stale; usage stores exist only for Claude accounts and are dropped with their quota source.

## Redirects and listing URLs (issues 245-249, 253, 254)

- `packages/llm/llm-pi-ai/src/no-redirect-fetch.ts:noRedirectFetch` — pi-ai request options accept a `fetch`; the adapter passes this one so a 3xx from a configured endpoint fails the request instead of replaying the POST body (conversation, tool data, inline images) at the redirect target, which a 307/308 would otherwise do cross-origin. Same-origin redirects are refused too: a POST replay is the exposure and a provider API has no reason to redirect one. The Google Generative AI and Vertex adapters reject a custom fetch, so those two protocols keep the default transport; that gap is unfixed and UNVERIFIED for the Google SDK's own redirect handling.
- `packages/llm/llm-pi-ai/src/adapter.ts:PiAiAdapter.streamWithSnapshot` — attaches `noRedirectFetch` to the pi-ai stream options for every protocol except the two Google ones named above.
- `packages/llm/llm-pi-ai/src/discovery.ts:discoverModels` — the listing request uses `redirect: 'manual'` and rejects any 3xx with an error naming the status and telling the user to configure the final URL. Standard Fetch strips only `Authorization` on a cross-origin hop, so `x-api-key`, `x-goog-api-key` and deployment-owned secret headers would reach the new origin; manual handling keeps all of them at the configured origin. Following a redirect under an origin policy was not built; the safest default is refusal.
- `packages/llm/llm-pi-ai/src/discovery.ts:discoverModels` — a non-2xx listing response has its body cancelled before the sanitized status error is thrown, so a long or never-finishing error body cannot hold the connection after discovery has reported failure.
- `packages/llm/llm-pi-ai/src/discovery.ts:listingUrl` — the base is parsed as a URL: the path gets `/models` (or Anthropic's `/v1/models`) appended to its pathname, existing query parameters are kept and the page-size parameter is set on the query, and the fragment is dropped because it never reaches the server. Plain string concatenation put the suffix inside a query or fragment.
- `packages/llm/llm-pi-ai/src/discovery.ts:readListing` — the OpenRouter-style `architecture.input_modalities` array is read into `inputModalities` when it holds recognised values (`text`, `image`); an absent or malformed field leaves the field out so the picker keeps its text-only fallback for unknown capability.
- `packages/llm/llm-pi-ai/src/discovery.ts:ANTHROPIC_MODEL_LIMIT` and `src/discovery.ts:GEMINI_MODEL_LIMIT` — the largest page size each public listing accepts; discovery now follows `has_more`/`last_id` (Anthropic, sent back as `after_id`) and `nextPageToken` (Gemini, sent back as `pageToken`) instead of returning the first page as the whole catalog, so these are page sizes, not model ceilings.
- `packages/llm/llm-pi-ai/src/discovery.ts:MAX_PAGES` — a listing that still continues after this many pages is refused with a hand-entry message rather than returned incomplete; the same loop refuses a repeated cursor, and a shared byte budget bounds the pages together.
- `packages/llm/llm-pi-ai/src/discovery.ts:nextCursor` — reads the protocol's continuation field; OpenAI-compatible listings have none and are single-page.
- `packages/llm/llm-pi-ai/src/discovery.ts:modalities` — keeps only the recognised `text` and `image` values of a declared modality array.
- `packages/llm/llm-pi-ai/src/discovery.ts:fetchPage` — one listing request: manual redirect handling, error-body cancellation, bounded read under the shared byte budget, JSON parse.
- `packages/llm/llm-pi-ai/src/discovery.ts:discoverModels` — a catalog provider whose drafted `baseURL` differs from the catalog's own endpoint is interrogated over the network instead of answered from the bundled list, because the bundled models are not evidence of what an overridden gateway serves; an unchanged or empty endpoint keeps the catalog answer. When the draft names no protocol the catalog's own model protocol is used for that probe. The `packages/llm/llm-pi-ai/src/discovery.ts:discoverModels` result carries no flag saying whether each model came from the live listing or the bundled catalog: that needs an `LlmDiscoveredModel` type change and picker wording, and is a decision for the lead.
