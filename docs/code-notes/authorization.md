# authorization code notes

## A record-updated event only confirms the attempt when it comes from the attempt's own writes (finding 293)

- `packages/credentials/authorization/src/index.ts:AuthorizationService.attempt` - the confirmation listener used to set `committed` for any `credentials/record-updated` on the flow's key, so a concurrent same-key write by another actor, or an external edit observed during the run, made a flow that wrote nothing report `authorized`. The flow now runs inside an `AsyncLocalStorage` scope holding the attempt's `InFlight` state and the listener only counts an event whose emitting async context is that scope. `credentials-local` and the other providers fan the event out synchronously from inside the writing call, so a write made by the flow, including one made through a provider-owned adapter such as pi-ai's store, carries the scope while a write from any other context does not.
- `packages/credentials/authorization/src/index.ts:AuthorizationService.attempt` - `session.commit` runs its `modifyRecord` inside the same scope explicitly, so it is attributed even when a flow calls it from a callback created outside the scope. Known limits: an adapter that performs the write from a worker loop created before the attempt loses the scope and reads as not committed; a flow deleting the record followed by an unrelated write in the same attempt still passes the configured check, because the event carries only the key.

## The commit protection ends with the write, and a withdrawal during a write is replayed after it (finding 294)

- `packages/credentials/authorization/src/index.ts:InFlight` - the old `committing` boolean was set before the write and never cleared, so after a commit the attempt could never be cancelled: a flow that committed and then hung, or caught a failed commit and waited, kept the key in flight until the host restarted, and a withdrawal that arrived during the write was dropped. It is now `writes`, a count of session writes in flight, plus `pendingWithdraw` and `saved`.
- `packages/credentials/authorization/src/index.ts:AuthorizationService.withdraw` - explicit `cancel()` and caller-signal withdrawal both go through it: with no write in flight it aborts at once, otherwise it records the reason so the request is retained.
- `packages/credentials/authorization/src/index.ts:AuthorizationService.attempt` - the `session.commit` wrapper decrements `writes` when the write settles, marks `saved` on success, and applies a retained withdrawal once the last write has settled. A withdrawn attempt whose commit was saved and whose record is still configured settles as `authorized`, not `cancelled`, so a durably stored credential is never reported as discarded; a withdrawn attempt with no saved commit, including one whose write failed, settles `cancelled`. Decision for the lead: the saved-then-withdrawn case reports `authorized`.
