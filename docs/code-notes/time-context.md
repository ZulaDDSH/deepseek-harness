# time-context code notes

`packages/context/time-context/src/index.ts:apply`: finding 233 showed that the refresh interval returned before the current request's browser-zone policy was derived, so a zone change, a mixed-zone steer or a missing zone arriving within the interval left the model with the previous reading's stale instruction. The policy line is now derived at every eligible step and the interval only suppresses a reading when that line equals the line carried by the latest injection, which the projection records in `lastBrowserPolicy` (state version 4, read from the policy line of each injected reading, so no event shape changed and older version 3 rows rebuild from the journal). A zone that fails validation during a step the interval would have suppressed still does not fail that step, matching the earlier behaviour: the step proceeds without a reading and the refusal surfaces at the next step that is not suppressed.

`packages/context/time-context/src/index.ts:apply`: the projection fold extracts the policy line with the `Browser time zone for this request:` prefix produced by `packages/context/time-context/src/request-zone.ts:renderBrowserTimeZoneContext`; a reading without that line records null, which forces the next step to inject.

`packages/context/time-context/src/request-zone.ts:reportedBrowserTimeZone`: finding 358 showed that an empty continuation prompt is recorded with source kind `retry` carrying the validated `clientTimeZone`, and the reader accepted only kind `user`, so the next request reported the browser zone as unavailable; both kinds now contribute, and the projection fold shares this reader so a replayed log derives the same zone.
