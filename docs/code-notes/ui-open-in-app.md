# ui-open-in-app code notes

`packages/client/ui-open-in-app/src/client/open-path.ts:OpenInAppPathController::openPath`: finding 229 showed that the open and reveal call carried no cancellation signal, so Gateway applied no unary deadline (the Remote method declares a cancellation parameter), the Host awaited the native opener without a bound, and the button that issued it stayed disabled until the promise settled. The call now carries a signal that joins the controller lifetime with a timeout (`openTimeoutMs`, second constructor argument, default 30000 ms); Gateway forwards that abort to the Host, which already terminates the native command on abort. A timeout resolves like any refused open, as the `openError` or `revealError` failure, so the control is enabled again and the user can retry deliberately. The failure text does not distinguish a timeout from a refusal and an opener that had already launched its target may still have done so before stalling: the outcome of the launch is unknown. The plugin composition keeps the default; no Config field was added.

`packages/client/ui-open-in-app/src/client/controller.ts:OpenInAppController.load`: the first availability read used to be memoized permanently, so a transient network failure left the directory controls hidden until the page reloaded (finding 228, client directory half). A read that fails (transport error, non-OK status, or malformed payload) still publishes an empty list but clears the memoized promise, so the next `load()` retries; a successful answer, including an empty one, stays memoized. The desktop-availability read in `open-path.ts`, Host-side discovery caching in `packages/host/open-in-app/src/index.ts`, and directory-path mapping for remote workspaces (finding 227) are not changed here.
