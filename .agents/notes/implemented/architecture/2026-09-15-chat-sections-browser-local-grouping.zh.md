# Agent Note：对话分组作为浏览器本地组织层

Status: implemented

[English](2026-09-15-chat-sections-browser-local-grouping.md) | 中文

## 问题

侧边栏此前只能按工作区对会话分组。`ClientWorkspaceModel.sessionIds` 是 Host 持久化的成员关系，同时决定会话的工作目录，而浏览器的各个 `分组方式` 模式（按工作区、按工作区树、单列表、活动）都只是对同一份成员关系的重新投影。用户若想把「代码评审」和「调研」并排放在一起，没有任何办法表达：注册一个工作区会改变会话的 `cwd`，而这并不是他们的诉求。

对需求最直观的解读是在工作区旁边再加一个分组实体。这个解读不符合需求，原因在于能力接缝：工作区不是分组标签，而是环境——它提供指令、文件、Agent 配置和工作目录。任何复用 `WorkspaceView` 的方案都会继承这些语义，而任何新增平行持久化注册表的方案都必须逐项回答某个能力是否由分组承载。需求明确指出分组不承载其中任何一项。

剩下的就是放置问题：一个纯标签加成员关系的层应该放在哪里，以及它是否需要 Host？

## 决策

**对话分组是浏览器持久化视图状态中的一个字段，而不是 Host 实体。** `stores.ts` 在与分组展开状态、手工会话顺序相同的 `dsh.workspace.view.v5` 值中声明 `chatSections`：`sections`（id 加名称，按显示顺序）、`collapse`（每个分组的折叠状态）、`members`（会话 id → 分组 id）以及 `sectionOrder`（每个分组的顺序）。该层不跨网络传输，`ctx.workspaces` 也未被触及。

持久化介质服从事实本身。分组是用户本已可见的会话之上的显示偏好，而不是权威业务状态；让它持久化将需要 Host 注册表、流、第二种持久化格式的迁移策略，以及对无头运行而言分组意味着什么的决策。这些都不是「把两个对话放在一起」所能换来的，而现有的视图存储已经正好拥有这类事实。

**分配引用生成的分组 id，而不是名称。** `newSectionId` 在客户端通过 `crypto.randomUUID()` 生成，并与其他动作回调一起通过注入面到达浏览器。因此重命名分组不会重新绑定任何东西，两个分组也可以同名而不成为同一实体。一个会话至多属于一个分组：`assignSession` 在把会话插入目标分组头部之前先将其从原分组移除，而未分组的情况则直接删除该成员记录。

**删除分组只删除分组关系。** `deleteSection` 移除分组记录、其折叠标志、其保存的顺序以及所有指向它的分配；会话保留其日志、工作区成员关系和顺序账户，并重新出现在未分组列表中。这与工作区删除已声明的保留边界相同，也正是这个破坏性动词无需数据丢失警告即可安全使用的原因。

**分组面板堆叠在工作区面板下方；它不是一种分组模式，也绝不取代任何模式。** 浏览区域在上方渲染所选的 `分组方式` 投影，并在 `sectionsActive` 为真时于分隔线下方渲染分组面板。两个面板各自独立滚动。这种形态使该特性纯属增量，它取代了两个被否决的草案。第一个草案让分组投影在任何分组存在时无条件优先，从而永久隐藏了工作区、单列表和活动视图。第二个草案让分组成为第五个 `SessionGroupBy` 取值，使模式菜单承载它；这恢复了切换，但仍把两者呈现为同一槽位的互斥占用者——用户必须离开工作区列表才能看到自己的分组，而且颜色/图标筛选不得不被抑制，因为它针对的是工作区行。

**分组是工作区列表之上的已保存视觉筛选，而不是第二份成员关系。** 每个对话仍然位于上方的工作区文件夹中；把某个对话归入分组只是把它加入下方面板，并不从文件夹中移除任何东西。同一个对话可同时出现在两个面板中，这正是用户陈述的模型，也是该面板不渲染「未分组对话」桶的原因：未归类的对话并未丢失，它只是在自己的工作区里。`deriveSections` 仍返回未分组的剩余部分；该面板并不渲染它。

因此 `sectionsActive` 只决定面板是否存在——任何分组（空分组也算，因为其标题正是对话落入之处）或任何分配——绝不决定哪个工作区投影显示。

**跨面板归类需要显式的拖拽通道。** 两个面板是各自拥有私有拖拽状态的独立组件，但归类是一个从工作区行开始、在分组标题结束的手势；任何一个面板都无法读取另一个面板的 React 状态。此前该包中的每一次拖拽都是面板内的，因此树的放置处理器以自己的 `workspaceDrag` 为门控，从别处开始的拖拽永远不会触发。`drag-bus.ts` 只发布进行中的会话 id；分组面板订阅它并拥有分配提交，而工作区树保留对自己重排序的独占所有权，因此跨面板放置不会既归类对话又把树翻转为手工顺序。

**分组标题本身，而不仅仅是行，也是放置目标。** 拖到标题上或该分组块内任意位置的对话都会加入该分组，这是折叠状态或尚为空的分组所需的指针路径。拖到同级对话上则插入到该位置，把一个分组标题拖到另一个上则重排分组。拖拽只是加速器，绝不是唯一途径：会话行菜单带有 **移动到分组 → [名称]** 和 **从分组中移出**，两者都由悬停菜单和上下文菜单共享的同一个 `sessionMenuItemsFor` 构建，因此二者不会分叉。该动作同样存在于工作区面板中，因此可以从对话实际所在的位置归类它。临时新会话行的交互规则不变——在首次提示之前它始终不可拖拽且不归类。

**新增字段通过显式的存储步骤迁移。** 持久化键在尚无 `chatSections` 时就已发布，而引擎通过整值替换进行再水合，因此对该字段的每次读取都会看到 `undefined`。`StoreSpec.migrate` 是新增的接缝：`attachPersistence` 在实例接受解析后的值之前对它运行该迁移，而 `ui-workspace` 声明了 `migrateViewState`，它从 `emptyChatSections()` 填充该层并逐字段规范化不完整的层。因此，在此特性存在之前写入的载荷会以零个分组、每个既有会话均未分组的状态加载，这是声明的兼容性要求，而不是副作用。

## 考虑过的替代方案

**镜像工作区的 Host 持久化分组注册表。** 被否决，因为它为该特性并不具备的能力付出代价。它会增加一种持久化格式、一个 REST/Remote 接口、一个后续流、第二个排序权威以及跨机器一致性方案——只为存储一个每浏览器的显示偏好。它还会强行引出需求已经裁定过的会话成员关系问题：分组是「零或一」，用一个映射即可表达，而注册表则意味着工作区形态的多对多机制。

**把分组作为工作区子类型并禁用其环境能力。** 被否决，因为它让环境成为默认、让缺席成为例外。每个工作区消费者——选择器、会话首屏、工作目录解析、已删除工作区重新分配——都需要加一个分组判断，任何遗漏都会给分组一项该特性承诺它不具备的能力。这两个实体除标题和有序成员列表外不共享任何字段。

**把分组成员关系存储在会话记录上。** 被否决，因为客户端不拥有会话记录。`SessionSummary` 是 Host 会话日志的投影；写在它上面的浏览器本地标签要么在下次列表拉取时丢失，要么被迫进入一种其唯一消费者是某个浏览器侧边栏的持久化格式。在浏览器已经持久化的视图状态旁维护一个映射，是更小且范围正确的归宿。

**复用 `groupExpansion` 和工作区顺序账户来存分组。** 被否决，因为生命周期不同。`retainAccountKeys` 会依据实时工作区列表裁剪那些记录；分组记录必须独立于任何工作区存续，而分组保存的会话顺序以分组 id 而非工作区 id 为键。共享这些字段会让工作区删除静默裁剪分组状态。

**让分组无条件优先于其他投影。** 构建后被否决：它使该特性破坏了既有导航。创建一个分组就会永久隐藏工作区、单列表和活动视图，用户再也无法切换视图或按工作区筛选——这是对既有能力的回归，而需求明确禁止这一点。堆叠面板在不夺走任何其他投影的前提下提供了同样的信息。

**把分组做成第五种 `分组方式` 模式。** 构建后被否决。它消除了上述破坏，但仍把两者保留为同一槽位的竞争占用者：查看分组意味着离开工作区列表，而且由于该模式替换了工作区投影，颜色/图标筛选不得不在其中被抑制——一个既有控件在用户并未要求进入的模式中消失。堆叠面板同时展示两者，并把每个工作区控件都留在原处。

**给分组加上嵌套子分组。** 刻意未构建。需求只要求一层，而嵌套会在一个无人要求使用的能力背后引入树结构、递归渲染路径和更深的成员关系模型。以 id 为键的状态日后无需修改格式即可接受它。

## 结果

- 分组层不会随会话迁移到其他浏览器、机器或配置。这是把它排除在 Host 之外的自觉代价，并已记录在包 README 的限制中，而不是作为缺陷呈现。
- 分组不改变会话的工作区、工作目录、日志、归档状态或搜索参与。搜索仍然投影可见会话列表；分组只决定这些行在哪里渲染。
- 工作区面板在任何情况下都保留其模式、排序和筛选控件：任何分组状态都无法从侧边栏移除既有控件。
- 分组面板上限为区域的 45%，因此很长的分组列表会自行滚动，而不会把工作区列表挤走；空面板或短面板则把其余高度留给工作区列表。
- 该包新增了一条小的跨面板拖拽通道（`drag-bus.ts`）。今后任何从一个面板开始、在另一个面板结束的手势都应通过它发布，而不是去读取兄弟组件的状态。
- 存储引擎在其持久化路径上新增了一个 `migrate` 步骤。今后任何加到已发布持久化键上的字段，都被预期在此处自行填充，而不是读取为缺失。
- `reconcileManualOrder` 被原样复用于分组成员关系，因此新发现的对话会按最近使用加入其分组而不丢弃已保存位置，悬空的分配则降级为未分组而不是丢弃该对话。
